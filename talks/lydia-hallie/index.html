学习手册 02 / Lydia Hallie

人不再盯着每一步，谁来接住责任？

模型越能长时间工作，开发者越需要把权限、环境与验收条件提前安排好。Lydia Hallie 把“少干预”拆成了一组可以检查的责任交接。

Anthropic · Claude Code 团队约 17 分钟演讲中文导读与讲解 · Lila
权限与沙箱验证节点长任务
导入

退出执行过程之前，先问谁来接手。

过去使用编程 Agent，经常要反复提醒、逐条批准命令，再把改动从头读一遍。Lydia 描述的新工作方式，是让多个会话在后台运行数小时，过程中自行验证，甚至由一个主会话协调其他会话。

这不是把旧职责删掉。她把原先由人承担的工作逐一拆开：谁理解目标，谁批准工具调用，谁限制程序运行时能接触的资源，谁证明任务已经完成？每少一次人工介入，就要知道哪一层接住了这份责任。

本篇要解决的三个问题
  • 自动审批为什么不能替代沙箱？
  • 怎样避免任务做完了，却不是你要的结果？
  • 什么时候可以从一个会话扩展到多个会话？
上手

先挑一项能回退的小任务，做一次责任交接。

下面是编辑设计的练习。先用一个低风险的界面或文档改动验证流程，再考虑长时间无人值守的任务。

  1. 写清结果：列出必须发生和不能发生的行为。
  2. 画出边界：确认允许访问的目录、网络和测试数据。
  3. 安排检查：把每项结果对应到测试、实际画面或命令输出。
  4. 观察卡点：记录哪些地方仍需要人决策，以及它为什么不能自行解决。
请先检查现有实现，再完成这项小改动。
完成条件：列出预期行为、必须保留的行为，以及对应检查。
只使用本任务所需的目录与测试资源；遇到新的外部副作用先报告。
完成后给出实际执行的命令、输出、被检查的版本和仍未覆盖的情况。

完成标准：能从报告追溯到实际检查；不能只有“已完成、测试通过”的结论。

指令

模型能从代码看到的事，不必反复写进指令。

Lydia 建议重新审视积累下来的 CLAUDE.md 和 Skills。早期用来纠正模型的“重要！”“永远不要！”不一定仍然有效；在她的描述中，过时或冗余的要求还可能增加工具调用、干扰执行。

值得保留的是代码中看不到、却影响决策的信息。例如某个服务仍在使用一项旧来源，而代码中没有对该来源的直接引用。相比复述技术栈，这类背景更能改变 Agent 的判断。

她也介绍了自动权限模式：由单独的分类器决定是否放行某些操作。若一个预发布流程需要推送到另一个仓库，默认只信任当前目录与仓库的配置可能拦下它。解决办法是准确描述信任边界，而不是把所有操作一概放行。

怎样判断一条指令该不该删？

先找它曾经防住的问题，再比较有无这条指令时的任务表现。能从代码推断，不代表每次都会推断正确；删除应有检查依据。这里给的是编辑建议，不是演讲提供的通用删减清单。

转写把一项审计命令记为“Dr. Prompt Audit”，精确命令拼写未确认。本篇不把它改造成可复制的操作步骤。

边界

允许启动一条命令，不等于允许它接触所有东西。

她提出一个判断标准：如果模型这一次判断错了，结果能不能收回？可回退的代码修改，与丢弃未提交文件、让密钥进入会话记录，不是同一类风险。

权限规则用于决定某次工具调用能否执行。但一个看起来普通的 npm test，内部可能运行项目依赖或新写的脚本。只批准了命令的名字，并没有检查这些代码会访问哪些文件、连接哪些服务器。

沙箱把约束下放到运行环境：限制可读文件、可写目录和可访问主机，让子进程也受到约束。Lydia 同时提醒，这种 shell 沙箱并不等于整个会话都处于隔离环境；她提到的 MCP 服务器、Hooks 等还需要分别审视。

在云端使用新仓库副本，可以避免把本机未提交的文件和个人密钥直接带进去。需要外部服务时，也要控制密钥与网络。演讲里的具体默认策略不能代替对自己环境的实际核查。

验收

同一个“迁移认证 API”，可能做出三种合理却不同的结果。

Lydia 用认证迁移说明目标中的空白：一个会话可能保留旧 API，一个只迁移新登录用户，另一个把所有人都登出。单看“迁到新 API”这句话，三种方案都可能被解释为合理；真正的区别在业务约束。

因此，她建议把任务拆成有检查点的小步骤，提前写明“怎样才算完成”。例如先验证现有登录状态不会被意外打断，再验证新登录路径。模型需要看到实际失败信息，才有机会继续修正。

提示词适合表达期望；必须运行的检查，可以放进 Hooks 或 CI。她举到编辑后 lint、任务完成前相关测试、会话结束前整套测试等例子。

关于退出码：演讲强调返回 2 才能在相关 Hook 中阻止完成。官方文档按事件区分其行为；不是所有 Hook 返回 2 都会以同样方式阻止动作。接入时应查对应事件，不能机械地把所有脚本的退出码 1 改成 2。

协作

先让一轮任务可验收，再扩大并发。

每个会话有独立环境后，仍需要一条共同的合并标准。Lydia 把 CI 放在这一层：不论单次会话中发生了什么，所有 PR 都经过同样的检查。自动修复可以接收 CI 失败信息，但它不能证明检查本身覆盖了真正重要的行为。

人工审查强度还要按风险分配。她描述的团队会使用独立上下文的审查会话，并对发现的问题再次核查；文档改动、普通产品改动和高风险变更的人工要求不同。这是团队做法，不是所有项目应取消人工审查的结论。

进一步的编排让主会话负责拆分任务、发起工作线程、核对交回的结果，工作会话负责执行。讲者提到的产品仍处于演讲当时的具体发布阶段。对学习者而言，更可迁移的部分是职责：协调者不能只收“完成了”的消息，还要检查完成证据。

练习

把“少干预”变成一次可检查的实验。

自动模式允许 npm test，能证明密钥不会泄露吗？

展开参考分析

不能。入口审批与程序运行时能访问的资源不同。要核查依赖、沙箱和网络边界，也要确认其他组件是否在隔离范围外。

认证迁移的测试通过了，还要看什么？

展开参考分析

检查测试覆盖的是哪类用户、是否保留既有登录状态、旧接口如何退出，以及测试是否针对最终提交。通过的测试只有在对应需求时才有意义。

主会话收到了三个“完成”回复，就能结束吗？

展开参考分析

应分别核对交付物与验证结果，并检查合起来后的行为。独立完成不等于整项任务完成。

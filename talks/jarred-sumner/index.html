代码可以写得很快，先选一个你能验证的项目

从放弃 Rust 重写 Claude Code，到反复改写 Bun 的提前编译器，看一套独立的测试怎样决定工程路线。

Anthropic，Bun 创始人约 22 分钟演讲中文导读与讲解 · Lila
Bun差分测试可验证的重写
导读

写得出运行时之后，谁能证明你还保住原来的行为？

Jarred Sumner 有过把 Bun 从 Zig 改写到 Rust 的经验。旧 TypeScript 测试可以直接对着两份实现跑。到了 Claude Code，设想把应用也改成 Rust 时，团队发现要一起改写部分用于判断行为的测试。实现和判定标准同时变了，出现绿色结果时就难回答到底是哪一边变了。

团队把目标拆回原问题。Claude Code 启动等待、内存开销、编译所需的时间，是不同观察量。把编译工作提前到构建阶段可以少做重复运行时工作，也会把一部分等待移到构建时。演讲保留了数轮实现的取舍，适合学习怎样在大量生成代码之外保住可以独立比较的证据。

读完可以做什么
  • 在换实现以前盘点哪些断言能够原样使用。
  • 区分首次编译耗时、启动耗时、稳态表现和内存。
  • 用同一批输入对照 JIT、AOT 和去掉类型信息的路径。
上手

用同一套行为检查验证两份实现

选一个熟悉的小 CLI，或在本地构造只会读字符串、输出结果的教学工具。固定输入文件、执行环境与版本。老实现应提供可以重复运行的观察记录。

第 1 步

先冻结几件真正要保住的事

正在改写时才写新的验收，容易把新实现的意外变成预期。

展开可复制的提示词
列出旧实现输入、输出和退出状态，选正常、非法和边界输入各一组。记录已知行为，并把期望独立存下来。先不要改任何测试断言。

完成标志　另一位开发者能拿同一批输入重复得到同样结果。

第 2 步

只变实现路径来做对照

如果输入、编译器和运行环境一起换，差异很难定位。

展开可复制的提示词
给出两次运行命令。复用相同输入、断言和环境，分别执行旧路径和新路径。列出每处不同，分为预先约定的变化、意外差异和需要人工查明。

完成标志　有可追踪的运行日志，结果分组可以回到原需求审核。

第 3 步

有意制造一个可识别的错误

稳定跑绿的长期检查也可能没触到关键代码。

展开可复制的提示词
只在本地测试副本注入一个已知错误，例如合法输入返回错误退出状态。先证明旧断言会变红，再还原。写下能捕捉它的断言。

完成标志　这条检查先红后绿，目标错误与失败原因对应。

第 4 步

写清性能提升发生在哪个阶段

一次启动变快可能以额外编译时间为代价。

展开可复制的提示词
保存冷启动、已完成编译后的启动、编译耗时和峰值内存。逐项注明测量区间，发现某组配置持续较慢时保留结果并解释。

完成标志　不把不能直接比较的阶段合并成一个速度倍数。

第 1 节

让验证能力决定方案

对一次大改动，最先找的是旧版本里可以继续当验收依据的东西。它的独立性会改变哪些方案做得起。

回看这一节 · 05:19:18 ↗

一次重写能不能独立验证，要看旧证据跟的是语言还是行为。Bun 的测试从使用者可见的界面去检查，两套实现都可以接受它。若测试和实现绑在同一语言的内部细节，迁移时就要单独想办法抽出行为基线。越早盘点这些入口，越容易估算真正的改写成本。

在应用层选型时，还可以找哪些行为从外面观察得到。退出码、标准输出和持久化结果可以固定在测试里；只有某种实现语言内部才能看到的变量通常不适合作为兼容判断。若有些老行为还没记录，在重写前先挑关键路径补观察。修改测试时把需求变化和执行工具迁移分别记下来，审查者才能解释某个断言为什么不再适用。

第 2 节

测量提前编译的收益

对比 AOT 和 JIT 时，要分别看构建成本与运行成本。一项一次构建、多次运行的任务，和一项每次都生成动态代码的任务需要不同实验。

回看这一节 · 05:24:18 ↗

演讲使用的 Claude Code 工作负载中，讲者报告内存大约降到四分之一，启动大约达到原来的两倍速度。图中只比较内存，以原来为 100 做归一化。应用的行为差异与构建代价需要另外看，动态求值较多的程序也是讲者提出的限制。

“把工作提前”会使同一优化在不同用户场景里的价值变化。习惯于装一次后反复启动的人，可能更在意每次冷启动；每改一次代码就要重编的人，则承受迭代速度。团队在演讲中继续推翻一版已经接近发布的实现，原因之一就是编译过程本身耗时超出其预期。记录累计花多少时间，比只报一次成功运行的耗时更贴近使用。

第 3 节

对照不同执行路径

同一批输入交给旧实现和候选实现。差异出现以后，先查哪条行为是约定，哪条是需要明确记录的改变。

回看这一节 · 05:26:17 ↗

教学推演。让一个小 CLI 分别读取正常值、空文本和不符合类型标注的输入。三路程序应当对正常输入给同样的输出。若只有 AOT 在空文本时给零，先重跑并保存足够小的输入，再检查是否某条特化假设把空值当成了合法数字。这个例子与实际 Bun 缺陷无关，练的是怎样把一个笼统的“编译器行为不同”缩到可以复查。

既有 Bun、WebKit、test262 和 Claude Code 检查来自不同层次。语言一致性套件能检查语义，应用测试能说明常用路径是否继续正常。把各自覆盖对象写到记录中，工程师才知道一次失败接下来要去找语言本身，还是去找应用调用方。也要列出已经明确接受的兼容性变化，避免为了让表格全绿把差异随手抹掉。

第 4 节

开发阶段不同，并发方式也要调整

先看一轮工作需要多少共享状态，再决定是否拆给多个人或 Agent。构建与修复的粒度可能不同。

回看这一节 · 05:28:19 ↗

设身处地读早期并行实现。三位工作者分别负责语法分析、表示变换和运行代码时，全量构建可能在接口还没接齐的地方反复失败。应先让每人记录当前局部已经能观察到的结果，等接口稳定再交叉运行端到端样例。进入修缺陷阶段则需要持续追踪触发条件，一次次重开会话会消耗角色对故障上下文的理解。这个例子为了说明阶段差别，并非本场内部任务清单。

第 5 节

让每次提速都留下可对照的记录

任意两版都应能用相同条件比较。除了最好看的一项指标，也盯住影响用户的构建、运行、资源和兼容性变化。

回看这一节 · 05:35:04 ↗

每小时的记分卡给了团队一个更便宜的追问方式。某次整体指标下降，可以回看发生在编译时间、启动速度，还是具体兼容性用例；后面即使换了实现，也至少还能用一份稳定记录比较。练习中也应保留改动前后的原始输出，避免最容易讲清楚的一项指标挤掉真正用来做取舍的检查。

做小时记分卡时，可以让一行对应一次构建而不是一个团队的总结。一边列测试套件、冷启动时间、编译耗时和内存来源，另一边列本次改了哪些测量条件。两次记录使用同样输入才计算变化；不一样的项目另记原因。这种留痕也能读出哪一步引入成本，避免把后来的 p50 或一个独立 benchmark 与更早的冷启动口径拼在一起。

演讲举到 UglifyJS，说明动态求值比例较高时，AOT 对一个应用的收益不能从别的程序外推。复现设计里先记录进入优化路径的条件，再收一组无法持续利用的负例。若一条替代路径能够运行但频繁退回另一种执行方式，结果需要随输入类型报告，不能直接归为整个编译器普遍无效。

练习

用这一讲的方法做一次小练习

一个 Agent 同时改了实现和测试，怎样恢复独立的验收依据？

展开参考答案

对照原版本中的测试、历史输入输出或仍在运行的旧实现。先用原条件重放新增实现，单列确实有意改变的行为和审批依据。

给 JavaScript 命令行工具安排一次 JIT 与 AOT 对照。

展开参考答案

固定硬件、输入、版本和启动次数，分别记构建耗时、冷启动、内存、运行时间和输出。再加入一组动态求值或边界输入观察兼容性和回退。

经过三种执行路径的差分测试，是否足以宣布所有应用兼容？

展开参考答案

它支持经过测试的输入和行为。增加边界参数、语言特性和真实项目，再用已知故障验证比较器确实会报不一致。

一份适合团队追踪的记分卡需要几类信息？

展开参考答案

写下构建与运行版本、统一负载和上版基线。列出运行速度、构建时间、内存和检查结果，保留故障与刻意调整的兼容行为。

导读

一条客户录屏能不能走到可验收的修复

客户在 Slack 里发来一段录屏，工程师把它转交给 Devin。Walden Yan 在演讲中展示了后来返回的东西：一个可以审查的 PR，还有一段复测录像。对于报告问题的人，录像让他们直接检查异常是否仍在。对于负责发布的人，PR 和验证环境则留下了可以核对的细节。两类人不必在同一层看同一份证据。

这个短片之所以能出现在汇报里，背后有一连串具体工作。临时机器先要能启动应用，需要外部服务时得有替身，Agent 还要知道怎样走到出错的那一步。Cognition 进一步把运行留下的痕迹用在两个地方：发现交付流程的浪费，以及把会反复出现的工作交给一个持续有输入、有检查的任务。读这篇时，可以用自己的一条小故障跟着走，看看哪一步正在等人补条件。

读完可以做什么
  • 把一张报障单写成可以复现的任务
  • 让来自全新环境的验证进入 PR
  • 为持续任务设指标、触发和交还条件
上手

拿一次客户异常做完整交接

教学案例：购物车保存后，快速连续点击有时生成两条记录。示例只在可重置的测试环境处理。要交付的是一份可以复现、修正、重新验证的改动，并能说明哪些结论来自哪一份证据。

第 1 步

写一张能按着做的报障单

越早告诉执行者期望动作，一次录屏越容易变成可以被追踪的修复任务。

展开可复制的提示词
在测试环境操作。输入是一段购物车录屏、失败构建号、可重置的测试用户。先输出复现脚本或逐步操作说明，写清前置数据、实际结果和期望结果。任何不可缺少的事实没查到，就列为阻塞项。

完成标志　输出记录里有构建号、测试账号、点击顺序，以及保存前后的记录数。记录指出哪个现象触发失败，能交给另一名同事重复操作。

第 2 步

在一台干净机器上重跑

已经预热的机器常残留浏览器状态、数据库或环境变量。干净环境能把应用缺陷与环境问题分开。

展开可复制的提示词
从当前测试分支建一份干净环境，使用可重置的测试数据和模拟支付接口。写出启动、种子数据、运行复现及清理命令，分别保存命令退出状态和复现录像。只能使用测试凭据。

完成标志　按文档从空状态启动后看到失败。发现依赖启动失败时，证据把故障归到环境。任何关键准备需要临时手工补救，都记入复现说明。

第 3 步

把修复和反例一起交回来

修复录屏证明一条可见行为。回归用例能在以后同样的改动里重新执行。

展开可复制的提示词
实现最小修复。新增一条快速连续点击只保存一条记录的回归用例，加一条正常慢速提交仍成功的检查。用同一测试用户和同一观察点录制改动后流程，返回 PR、命令、执行结果与录像位置。

完成标志　PR 里能找到同一输入下的修复前后记录数。失败截图对应原版本，成功截图与实际 PR 提交关联。能正常完成普通保存。

第 4 步

定义持续观察与移交条件

执行者可以收集某类信号。指标口径、用户影响和发布由负责小组决定。

展开可复制的提示词
为该行为写一张一周跟踪卡。说明在哪个流量环境观察、用哪个版本作起点、如何收集重复记录、什么时候汇报、发现支付或生产数据风险时交给谁。给出一条可读的示例汇报。

完成标志　示例汇报能区分本周观察、对应样本数、候选改动、待确认问题。生产写入或发布等要另由负责人确认。

第 1 节

合并量增加之后，谁决定该做什么

Walden 从两条增速差距很大的内部曲线开场。他在意的问题是，工程团队要怎样安排工作，才接得住 Agent 新增的实现能力。答案先落到组织上。负责一个产品面的工程师要同时知道客户哪里卡住、什么算修好，以及下一步做什么。

回看这一节 · 02:33:35 ↗

Walden 把合并 PR 的图放在小组职责变化之前，读图时可以先拆开两层。第一层是统计：同一时期，人员和合并量都发生了变化。另一层是工作安排：Cognition 把大团队拆成更小的产品小组，给小组更完整的职责，包括客户反馈、QA、产品判断和任务安排。演讲的案例说明了团队怎样应对更高的交付量，图里没有分别测出每种做法带来的增益。

拿去做内部分享时，可以把指标翻成两个问题：并行实现之后，谁还有权调整范围？每个人的工作能一起收进哪个验收点？若同一客户问题牵涉两组，而两边独立叫 Agent 改各自服务，合并量可能升上去，交付仍然得等核对。小组能否接住工作，看的是它是否知道谁决定功能、谁可以确认行为，谁可以把改动移交发布。

第 2 节

一条故障视频，怎样传到验收

Slack 示例的两个视频分别回答了不同的问题。客户的视频让异常可观察，修复后的视频让团队能核对同一个动作。看这段时，可以把两段视频之间缺了哪些证据当作自己的检查题。

回看这一节 · 02:36:50 ↗

转发故障录像只把用户看到的表现送进流程。有时从画面看到重复请求，却看不到哪个版本、哪个账号，或是否有重试。交接者先补这些字段，Agent 才能把视觉线索变成可重跑的输入。修复录像能回答「这条路径现在怎么表现」，还要由能重复执行的检查发现后来提交是否又破坏了它。

同一条客户报障落地后，面向不同读者分发证据。客户需要看到影响已消除；工程师需要核对提交、环境和运行记录；负责发布的人还要看监控和回退方式。演讲的 Slack 例子把这些线索以一条上下文串起来，修复前规划证据如何回传，往往比事后再补截图省力。

第 3 节

让 Agent 每次都拿到能启动的环境

从客户视频走到修复视频，中间最难省的是把程序跑起来。Cognition 的迁移把关键服务和模拟依赖装进一台虚拟机。每小时用新代码重建的办法，还把环境坏了这件事提前暴露给团队。

回看这一节 · 02:37:59 ↗

Cognition 将原先依赖云 staging、数据库和在线服务的测试场景移到一台可启动的虚拟机。Docker Compose 组织进程，外部依赖可用模拟实现。评价这个安排时，要先问模拟能力覆盖到哪里：一个支付替身能接收某个请求，仍可能缺正式支付供应商的限流、签名规格和回调延时。团队可以用它稳定工作循环，发布条件里还要写清真实跨服务验证在哪里进行。

以多人语音为例，能创建一个账号、跑通一个客户端，只能证明该进程活着。演讲描述在同一台机器让多个账号进同一房间，检查声音能否从一个参与者传到另一个。这里需要准备可重复的输入、确定接收侧的可观察点，还要能收集参与方各自的运行信息。一套更好的本地技能应该写清哪份信息能验证哪一步。

每小时重建用的是团队自身的节奏。收益来自及时发现依赖、镜像或启动脚本的变化，频率由代码变化率和构建成本决定。遇到构建失败，先标记快照状态；后续工作如果仍使用旧快照，应让 PR 记录版本。否则 Agent 可能交出一份在它的本地确实正确、在当前主干却无法重现的录像。

第 4 节

用运行记录来改交付流程

这里有两轮工作。第一轮把客户的问题修好。第二轮回头看很多次运行里的重复操作，找出适合写成脚本、前移到 lint 或缩短 CI 的步骤。下一次接同类工单时，就能观察这些改动是否真省了时间。

回看这一节 · 02:40:23 ↗

运行记录里通常同时存在等待、实现、重试、验证和人工接手。先选一类稳定的任务，按操作时间把几十次运行拆开，再看它们经常在何处返工。例如物料环境每次都重复安装依赖，就用同一锁文件选几次常见任务，比较改造前后耗时和失败模式；一些提示词有固定内容时，也可以检查是否适合放进工具或仓库说明。

Walden 的 Slack 频道示例把观察和修改接起来。Agent 可以整理已经发生的例子、找出共同症状、提出小改动和复测方式，随后由维护者决定推进。进到改造后，重查耗时、回归失败和人工交接次数，可以区分「局部省时」与「工作转嫁到别的队列」。演讲举的 CI 节时数字是预计收益，使用时要保留测量基线。

第 5 节

从一次性工单到持续跟踪的指标

一次工单可以写成“排查上周某次超时”。持续工作得从测量开始。以 p99 为例，先把路径、采样窗口和基线写清楚，再让 Agent 调查有信号的时间段。把发布决定和指标目标分开写，团队才知道该在哪里接手。

回看这一节 · 02:41:21 ↗

p99 描述几乎最慢的那一端。教学时可把它看作 100 次请求中靠近最慢的一次，具体分位数算法和样本规模应看监控的说明。要让 Agent 持续跟这项工作，先指定用户路径、环境、时窗，以及业务量变化如何纳入比较。一次周报如果只报数字升降，却没有请求样本、部署版本或观察范围，就很难判断是否出现了性能变化。

计时和报表可以交给执行者，怎么处理风险由团队负责。如果尾部延迟变短但错误率上升，或依赖在低峰更快却在高峰更慢，就应把相关样本和最近的改动放进报告。GPU 试验同样需要限制预算、固定基线和明确哪些候选能进入评审。讲者给出了自家团队的内部结果，听众还需要工作负载、参数和配置才能做横向比较。

第 6 节

把 iOS 当参照，持续维护 Android 功能

Android 案例里的关键输入是一个跑得起来的 iOS 版本。它让“保持一致”有了可对照的画面和行为。案例也说明，即使人不用每天发消息，持续工作仍要有触发来源、质量检查和人工决定的路径。

回看这一节 · 02:44:26 ↗

Android 案例有两个源头。一条来自已经维护的 iOS 应用，给出了可以对照的功能行为；另一条来自 Slack 用户反馈，指出现实中遇到的障碍。团队用 QA 对照画面，把结果发回 Slack。举个练习中的例子。如果 Android 用户希望返回时保留草稿，而 iOS 会丢弃草稿，可以请产品组决定是否保留这一差异，并记录验收条件。

讲者报告经过 44 天有可运行的 Android 应用，并说大多数日子没人给这个 Agent 发消息，它仍在合并改动。演讲时应用准备发布；质量、上线之后的留存和长期维护成本要等后续记录。这个例子能直接复用的部分，是怎样给一个涉及多轮交付的任务建立明确输入、固定反馈和升级条件。

练习

用这一讲的方法做一次小练习

实作一。挑一个低风险的前端缺陷，写出 Agent 接手到人工验收需要的资料。

展开参考答案

给出失败录屏、版本和复现步骤，列出可重建的测试环境及一项回归测试。约定返回 PR 链接、修复后同角度录屏和测试结果。遇到需要生产权限或行为预期说不清时，交回人决定。

实作二。把‘页面有点慢’变成一个为期两周的 p99 改善任务。

展开参考答案

选定一个路由或用户动作，定采样窗口和基线，在代表性流量下观察 p99，同时监控错误率。每周提交趋势、调查证据和候选改动。涉及生产配置和发布时交给负责人审批。

理解检查。为什么一台能随时重建的 VM 会改变 Slack 报障的流程？

展开参考答案

每次接同类任务时可从可运行的近版本环境起步，在统一依赖下复现问题并产出验证结果，减少来回索要配置和等待测试环境。

理解检查。40 倍合并吞吐与 2.7 倍人员规模能支持什么结论？

展开参考答案

它们给出了 Cognition 自报的同一时期变化。要判断质量或是否可复制，还得看 PR 大小和类型、上线结果、缺陷、撤销和投入等口径。

理解检查。Android 的案例里，少发人工消息之后还依靠什么输入？

展开参考答案

iOS 代码变更、用户反馈、跨端 QA 及录屏仍持续提供信号。重要选择需要升级给人。

导读

让软件工厂知道什么时候该停

夜里收到一个告警，系统可以立刻准备一份改动。早上起来，工程师看到的可能是一条很有把握的说明，也可能是一份包含告警、复现、测试和待决问题的调查。两个交付都来得很快，反馈却只会进入第二种工作。Dexter Horthy 把让工作开始和让改动被检查画成两个方向，要求团队同时设计它们。

演讲还用不同返工代价说明什么时候值得先写规格。调整一个按钮随时可以撤回，已发布的数据契约有很多人依赖。这样的比较可以指引规格深度、测试和人工决策点。下面用一个要增加第二种通知渠道的教学练习，把「首版能跑」与「下一版还能改」分开观察。

读完可以做什么
  • 写清每个自动触发事件交给 Agent 的目标、证据和停止条件。
  • 按错误代价选择先试跑、先验收或先与相关方确认。
  • 给同一份代码追加后续需求，观察维护成本与证据质量。
上手

把一条可以回滚的功能改动做成验收练习

教学项目已有邮件通知，目标先增加可调标题，再新增一种通知渠道。两个任务分开给模型，第二轮记录哪些旧代码和测试仍能复用。整个练习只在本地项目运行。

第 1 步

把触发说明和验收关口放在一起

一张任务卡要说明为什么现在处理、什么结果有资格提交。

展开可复制的提示词
把“提醒内容不清楚”改写成一个小任务。记录现象、影响版本、希望保留的行为和最小候选变更。用固定样本写出验收条件，未能复现时让 Agent 停下来报告缺少什么。

完成标志　任务有实证起点，修改权限和停下条件都可以被他人复核。

第 2 步

先做一轮低代价的试改

视觉和文字上的决定通常更适合先拿出一个小样。

展开可复制的提示词
在通知标题支持一个可选前缀，默认标题维持原样。写一组输入与预期输出，先保存实际失败，再实现并重跑。说明是否涉及发信和外部操作，验收只使用本地假数据。

完成标志　新路径和默认路径都留下测试，负责人可以看到改动前后的不同。

第 3 步

分发第二个需求，检验第一轮留下的结构

两个任务一起给出时，模型早已知道未来的需求，无法模拟真实演进。

展开可复制的提示词
现在再告诉 Agent，第二种渠道需要沿用同一套标题或主题规则。比较复用旧逻辑和改动接口的代价，记录触及的扩展点、兼容风险及任何需要同意的默认变化。

完成标志　能指出哪些结构帮助第二轮复用，哪些地方的改动扩散到了不相干的组件。

第 4 步

留下别人可以快速核对的交付

提交说明写清楚什么发生过，才能让人承担发布决策。

展开可复制的提示词
输出一页评审包，列出初始意图、两次提交、检测证据、未覆盖的条件与建议的回滚点。报告生成内容的编辑核验范围。用一段最短的文字让接收者知道该批准什么。

完成标志　每项结论有可追溯来源。还未验证的业务行为保留为待办。

第 1 节

先看旧流程已经解决了什么

画出从一条需求到用户用上改动的流程，再标出 Agent 接手的工序。剩下的环节需要各自的证据和责任人。

回看这一节 · 08:18:33 ↗

如果把旧链路画出来，真正换人的可能只有「实现」一格。需求仍来自人或监控，候选改动之后还有检查、灰度、使用情况和回访。输入不稳定时，模型也许会把调查任务误做成修复。可以先写一条落地边界，先产出发生了什么，确认后再让改动进评审。

第 2 节

同时设计工作入口和质量关口

工单越容易转成改动，越要知道下游怎样验收。让系统先回收廉价、可靠的检查结果，再请求人处理须由人判断的部分。

回看这一节 · 08:19:55 ↗

假设夜间告警来自同一次短暂抖动，十条信号都开修复任务就会增加人早上合并重复 PR 的负担。队列先按负责人或影响范围聚合一次。只让自动化接收小范围的调查，报告已看到的证据，反复出现的可靠判断再进入可执行检查。

第 3 节

在下一项需求里检查可维护性

给评测增加一轮后续需求，比只看第一版功能是否跑通更接近日常开发。留意第二轮是否要大面积重写，以及测试是否还说得清系统行为。

回看这一节 · 08:22:39 ↗

演讲的 SlopCodeBench 把需求逐轮发给模型。团队可以用同样的试验思路看自家项目。第一轮只要求默认模板保持原样，第二轮新增通知渠道。若第一轮为了“未来扩展”建了大量无用接口，或把变化写死在发邮件的组件，第二轮都可以从改动范围和验证难度里看出来。

第 4 节

按返工损失决定先计划多少

写规格之前，估一估选错方向的概率和修正所需的时间。按钮配色可以直接试，看起来可逆的数据库结构改动也许会牵动长期兼容。

回看这一节 · 08:25:53 ↗

讲者用「需要返工的概率 × 返工代价」估计一项决定值不值得提前规划。用它审视通知练习，样式可以当天恢复，错误的数据契约要协调多个调用方。规格的篇幅应让工程师更容易验证高代价的承诺。

第 5 节

把试验、决策和证据留在一起

试验的规模可以小，复盘信息需要完整。为开关实验写下目标、启停时间、谁会受影响和怎么评估效果。

回看这一节 · 08:27:40 ↗

在工作结束时，把试验意见留在与实现相近的位置。未来的人需要知道某条默认值是在保护哪个历史调用者，为什么一次失败没有修复。简单的交付包能让讨论收敛。它给反复发生的问题一个可跑的检查，也给需要人判断的选择一个明确的负责人。

第 6 节

让读者花得起验收的时间

接收者只需要看到足以做决定的材料。提交人可以先理解生成内容，再用更短的叙述和可查证据说明交付情况。

回看这一节 · 08:30:14 ↗

一次评审只需要能做出本轮决定的材料。让审查者按候选提交、风险和回退线索打开，不用在文档中逐个验证泛泛的承诺。若生成的原始日志太长，保留一页核心证据再指向完整记录。

练习

用这一讲的方法做一次小练习

一个产品需求会直接启动 Agent。应在哪三处留证据？

展开参考答案

在入口记录任务如何触发及版本，在验收记录功能检查与关键失败，在发布后记录上线范围、回滚条件和用户反馈。

为“代码能接着改”写一道两阶段评测。

展开参考答案

第一阶段做分页列表，第二阶段再给筛选和稳定排序要求。比较两个检查点的行为、是否要大范围改写，以及已有测试能否复用。

按钮文案修改和支付数据结构修改，怎样分配计划时间？

展开参考答案

文案先出小样，由相关读者看懂且可快速回滚即可。支付结构先核对读取方、历史记录、迁移策略、兼容期和恢复测试。

同事收到一份又长又难核对的 Agent PR。提交人要补什么？

展开参考答案

先写改动要解决的问题、方案为何成立和仍需判断的两三处，再给对应的提交、运行过的检查和结果链接。把重复的生成说明删掉。

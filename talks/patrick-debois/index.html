先理解，再核对。
学习手册 03 / Patrick Debois

多个 Agent 都能写代码，为什么交付反而堵住了？

并行写代码只是开始。Patrick Debois 把问题延伸到任务认领、环境隔离、合并后的业务意图，以及团队共同维护的决策记录。

Tessl · Concurrent Delivery约 22 分钟演讲中文导读与讲解 · Lila
并发交付协作边界决策日志
导入

PR 变多之后，瓶颈开始向下游移动。

一个人同时使用多个 Agent，仍可能靠自己的记忆协调分工、处理合并。多人一起操作同一代码库时，这个办法就难以维持：每个人都有自己的会话、上下文和待合并改动。

Patrick 描述了几种压力：一个 Agent 把另一个刚改好的东西改回去；一次合并让其他 PR 重新变基、重跑测试；功能开发、Agent 故障和工厂维护同时挤进审查队列。写得更快，并不会自动让整条交付流程更快。

他提出从持续交付进一步走向“并发交付”：把多人、多 Agent 同时改变系统当作常态来设计，而不是每次冲突出现后再补救。

上手

拿两项真实任务，先做一次并发检查。

编辑练习：选两项原本计划同时进行的小改动，先把交接表填清楚，再让 Agent 执行。

  1. 分别写出负责人、目标和会修改的文件。
  2. 列出共享资源：端口、数据库、测试数据、外部 API。
  3. 写出可能变化的契约，例如字段名、金额单位、登录状态。
  4. 确定组合验证与冲突时的决策人。
请检查任务 A 与任务 B 是否适合并行。
分别列出：目标、文件范围、依赖、共享资源、对外契约和完成证据。
区分文本合并冲突与业务意图冲突。
遇到冲突时提出等待、重新排队或调整分工的方案，并说明代价。
不要仅因为修改的是不同文件，就判定两项任务独立。

完成标准：两项任务各自通过后，还能执行一次针对组合结果的检查。

分工

任务认领要写出来，环境隔离也不能只隔离代码。

Patrick 先从规划讲起。按认证、支付等模块拆分工作，比把同一个大任务同时交给多个 Agent 更容易协调。粒度也可以细到文件或函数，但拆得细不等于依赖就消失了。

任务开始后，要在共享看板上认领，并说明将改动的范围。其他 Agent 看到的是正在发生的工作，而不是最后才出现的一份 PR。这有助于提前发现重叠，仍不能保证模型会始终遵守约定。

Git worktree 为不同工作提供代码目录，但讲者把隔离范围扩展得更广：独立机器、固定上下文、锁定 API 版本、数据库快照和测试数据，以及模拟外部系统。目的都是减少执行期间环境不断变化造成的干扰。

独立工作树为什么还不够？

两个工作树仍可能连接同一个开发数据库，使用同一个端口或共享一份测试账号。代码目录没有冲突，运行时仍会互相影响。这里是根据演讲拆出的教学例子。

发生冲突后，可以等待、重试、重新排队，也可以重新协商任务。哪一种合适，取决于共享资源、依赖方向与等待成本。

意图

美元改成美分，另一份报表知道吗？

演讲中最值得停下来看的是发票例子：一项 PR 把金额计算的单位从美元改成美分，另一项 PR 同时调整报表输出。它们可能不修改同一行代码，甚至分别通过自己的测试，却在组合后产生错误。

文本能合并，不代表业务含义兼容。需要核对的不只是修改范围，还有单位、输入输出约定、状态含义，以及下游使用者的假设。

Patrick 还介绍了推测式合并列车的思路：提前检查候选改动的组合，减少队列中某项失败拖住其他改动的情况。这是协调与调度的方法，不是取消组合验证；额外检查也会消耗资源。

决策

共享看板不只是进度表，也是保存“为什么”的地方。

多人协作的另一半是人。Patrick 描述把 Agent 拉进团队已有讨论，让它从不同成员的意见中细化工单、明确测试和要求。销售、支持等角色可以更早参与，但仍要沿用团队的工程规范与交付流程。

Agent 卡住时，也可以让人带着同一份上下文接手，在 IDE 里做判断或实验，再交回自动化流程。这种混合方式保留了快速迭代的空间，避免每次都从头讲背景。

他强调把模糊求助变成具体选项，并把决定写进共享日志：谁在什么时候，基于什么条件选择了哪个方案。下一次会话应能查到它，其他人也能追溯。

编辑示例 · 一条可用的决策记录

问题：两个任务都要修改结算接口。
选择：先完成单位统一，再调整报表。
原因：报表依赖新的金额契约。
负责人：明确由谁确认契约。
失效条件：接口设计再次变化时重新讨论。

风险

审查多少，还取决于错了之后能不能恢复。

为了减少人的审查负担，先提高交付物质量是合理的：更准确的上下文、合适的工具、独立审查，以及截图、视频和测试证据，都可以让审查更集中。

但 Patrick 没有把“质量更好”当成唯一尺度。文档、尚无真实用户的实验与认证系统变更，影响面不同。人工审查、渐进发布、错误监控和恢复策略，需要一起考虑。

如果最坏结果是数据丢失，就要问能否恢复；如果是节点故障，要问能否回滚或切换。降低失败概率与降低失败后的损失，是两件不同的事。

他还提出“工厂团队”的职责：维护 Agent 所依赖的基础设施，保证 Skills 有负责人、上下文及时更新、执行过程被监控。更多自动化意味着新的维护对象，而不是没有维护工作。

练习

先把并发带来的隐性依赖说清楚。

两个 Agent 修改不同文件，是否就可以放心并行？

展开参考分析

还要检查共享运行环境和业务契约。不同文件可能读写同一数据库或依赖同一个金额单位，必须验证组合行为。

把每个 Agent 放进独立工作树，就能避免相互干扰吗？

展开参考分析

不能。工作树隔离代码文件，不自动隔离服务、端口、数据库、凭据或外部副作用。

一份决策日志只写“选择方案 B”够吗？

展开参考分析

还应保留决策人、时间、原因与适用条件。否则后续 Agent 无法判断旧决定是否仍适用。

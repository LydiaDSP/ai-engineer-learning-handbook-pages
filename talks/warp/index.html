学习手册 第二天 03 / Zach Lloyd

让软件工厂的工作流程也能测试和改进

Zach Lloyd 拆开 Warp Factories 的演示，说明怎样把工作流写进配置，在真实运行中测量问题，再重放团队任务，比较改变是否有效。

Warp · 创始人兼首席执行官约 18 分钟演讲中文导读与讲解 · Lila
软件工厂在线评测配置回放
导读

个人开了更多 Agent，团队开始改交付方式

同一个工程师能同时跑很多会话，仍要弄清谁负责工单、哪次尝试通过服务验收、生成的结果能不能一起合并。Zach Lloyd 将这一变化讲成一次工程对象的扩大。团队可以把 Agent 能接什么、在哪里执行、如何验收写成可审核的工作流，还要用完成工作的记录判断设置是否起作用。

在 Warp 演示里，配置记录授权的仓库和工具，运行中能看到发起会话的人、设置和生成物。评测从已经发生的运行找重复失误，例如生成了已有测试覆盖的检查。把这些线索送回配置，能用一次小范围试验验证团队究竟修好了哪一段。

读完可以做什么
  • 梳理一条进入、执行和验证的团队工作流
  • 用团队任务衡量改设置前后的结果
  • 分清任务失败、评测标记和实际的复查结果
上手

拿一个告警试着做成能回放的工作流

教学例：测试服务频繁发出转码耗时告警。输入是一份脱敏告警、固定提交、两份外观相近但原因不同的历史记录。要交付一张调查报告和可以审核的流程变更。

第 1 步

声明任务边界

把项目、数据和工具写进配置，团队成员能在任务跑起来以前看到执行范围。

展开可复制的提示词
写一份测试工作流声明，注明从哪种告警进入、读哪个仓库或日志、在什么沙箱执行。提供调查和验证的输出清单，说明缺信息时该停在哪一层。

完成标志　生产修改没有在入口获权，PR 清楚显示仓库、触发条件、输出和人工接手关系。

第 2 步

运行一个有证据的试次

单次结果足够暴露工作流缺了什么，随后可以抽样复跑。

展开可复制的提示词
跑一条已知测试告警。记录告警与版本，用固定命令收集延迟分布，给出候选原因和证据定位。将风险不明的结论标为待确认，提供能安全复跑的检查。

完成标志　每项判断能追到同一个快照。评审者能从工件定位日志和命令。

第 3 步

在历史运行里找共同模式

有多条相似记录时，可以集中找一个优先修的步骤。

展开可复制的提示词
抽取若干同类运行。按是否重复已有用例、是否遗漏边界、是否提早升级给人分类，每类列一个已检查的例子。区分评测器标记与人工复核。

完成标志　得到一条可操作的配置修改建议和至少一个会推翻该建议的例子。

第 4 步

一次只改能复测的变量

把结果绑到同一组题，适合发现哪里真的进步了。

展开可复制的提示词
在分支改一项，如在生成新测试前查询现有覆盖。冻结型号、任务和输入版本，用同一批任务回放旧配置和新配置，对照有效发现、误报、成功率、用时及审查成本。

完成标志　表里有测试样本、版本和数值定义。团队能据差异决定合并或回退。

第 1 节

个人提速遇到团队瓶颈

开更多本地会话能提高一个人的并发量。遇到重复工单或跨团队治理时，先想清楚哪些动作和策略需要在组织内复用。

回看这一节 · 01:01:24 ↗

本地并行会话的主要边界，在于它们通常只随着眼前任务完成。下一个同事想重复同一次处理，可能没有看到使用的模型、如何启动、先读过哪份约定。集成入口为团队提供稳定路径，从一张告警或工单把必要的上下文带进来。围绕小范围、经常重复的问题，先把输入到交付的关键状态做出来，比同时替换全公司的工具更容易检验。

第 2 节

把工厂定义写成能审核的配置

在 Lloyd 的定义里，软件工厂是一套用代码声明的闭环，用来持续衡量和改进云端编码 Agent。团队可以在分支中修改一条策略，再用相同的任务比较前后表现。

回看这一节 · 01:04:55 ↗

明确一条配置的版本之后，可以比较同一个请求在不同条件下怎样处理。比如新增一套测试工具时，把它先放进试点分支，用一批固定良好的记录回放；生产配置的变更应能看到人什么时候通过。将实际访问边界直接放到运行环境和权限策略中，也可减少在指令里重复写提醒。

第 3 节

运行记录和环境要能复用

重放之前先补齐材料。一次工作如果只剩最终 PR，就很难解释 Agent 在第几步耗时或退错方向。

回看这一节 · 01:10:36 ↗

团队开始看一张共享运行图时，三个数字容易混淆。吞吐是一个时间窗口有多少个可验收的结果；人工接触可能发生在胸有成竹的产品选择，也可能发生在修复流程故障；成本中还有失败重跑。若把触碰次数都当坏事，系统可能只是把必要的复核藏了起来。

第 4 节

用在线评测找出重复出现的问题

从一个能指认的失败模式开始。Warp 的冗余测试例子比笼统给 Agent 打分更容易追查。

回看这一节 · 01:14:38 ↗

演讲的冗余测试评分项适合处理工具有足够记录的场景。先将“与已有覆盖重叠”翻成一个可核对的例子，要说明既有测试在同一输入与状态下断言了相同结果。将评测器挑出的会话给维护者复核，区分重复覆盖、应补中的边界和暂时无法判定的旧记录。接着才决定改指令、调整测试搜索，或直接把判断放入工具。

第 5 节

用团队自己的任务检验修正

当前线上运行告诉人哪里出了问题，回放让人判断准备采用的配置是否更合适。比较时只改一个变量，更容易解释结果。

回看这一节 · 01:17:05 ↗

内部可复跑的任务可以向同一个验收人员展示两条路线。团队先找到有代表性的工作，固定版本和工单；替换模型、框架、Skills 或流程时逐项做试验。这能看到公开排行榜关心的能力是否刚好是团队痛点。结果表也要保留例外，持续暴露模型偏离业务规则的具体实例。

练习

用这一讲的方法做一次小练习

实作。选一类重复出现的低风险工单，写出可以放进版本库的工厂配置草稿。

展开参考答案

写出触发事件、允许的仓库、三步运行流程、保存的证据、升级给人的条件，以及观察效果的一项指标。

实作。针对 Agent 经常生成的冗余测试，写一个在线评分规则和一轮回放实验。

展开参考答案

定义重复覆盖如何识别并采样人工复核。保留原运行作基线，对代表性任务逐一回放。记录冗余、遗漏、额外耗时和费用。

理解检查。同一团队为什么需要线上评测和离线回放两种数据？

展开参考答案

线上分数指向实际流程中常出现的缺陷，回放让团队在更换配置前对照衡量预期改善与副作用。

理解检查。为什么要把会话、截图和工件保存在最终 PR 之外？

展开参考答案

它们记录了中途采取的动作和产出的证据，有助于追查同样的失败何时出现，以及哪些阶段消耗了最多成本和人工时间。

Brian Douglas 展示 Rust 代码通过编译和自动检查后仍被同事退回的过程，从会话标签开始，整理出内部评审规则和可重复的评测。

导读

当团队专家说“不这样写”，把原因留下来

Brian Douglas 说，自己缺少 Rust 开发经验，看到 Greptile 给 PR 打 5 分（满分 5 分）就容易放过它，人审时却仍会收到异议。他还见过同事提醒 Agent 遵守已有的 API 约定，或指出项目里已经有相同的服务。把这种反馈连同会话一起存下来，下一轮评审才找得到团队作出决定的依据。

他用 Tapes 记录会话和工具动作，再对反对、回退或表现特别好的例子做筛选。演讲所用的内部 Twin Reviewer 从这些实例里找评审习惯；讲者现场说明该工具有敏感内部数据。普通团队可以用脱敏任务先做规则、例子和回归集，从几次能独立验证的评审开始。

读完可以做什么
  • 从会话和 PR 中分别找到了什么证据
  • 将一条评审意见做成可以回放的案例
  • 用数据决定 Skill 的第二轮调整
上手

把一次结构性评审做成回归题

教学例：一条 Rust 变更新增了类似数据服务的实现，项目里已有近似服务。准备一条脱敏评审、原 PR 局部差异、相关已有接口，以及一个确实应该新增服务的反例。

第 1 步

保留引发反馈的上下文

一条单独的反对意见很难解释团队究竟不同意哪项决定。

展开可复制的提示词
读取脱敏材料，分开记录任务目标、当前 PR 的候选方案、评审指出的问题和维护者最后选择的做法。为每项保留文件位置或代码引用。

完成标志　卡片中找得到触发评论的具体代码，并知道判断来自编译日志、通用规则还是项目惯例。

第 2 步

写一条有例外的项目规则

规则覆盖所有名字相近的情况，容易把合理新增也挡住。

展开可复制的提示词
整理一条仓库内约定：新增项目内部服务前查哪些模块，什么叫已有服务能复用，什么情况必须保留独立实现。附一个建议复用的例子和一个正确新增的例子。

完成标志　规则指出事实怎么查、什么时候提问、允许例外的条件。示例不会带出未授权的会话内容。

第 3 步

留一批没给规则作者看的题

如果评审规则只是记住讲过的案例，无法帮助下一条 PR。

展开可复制的提示词
使用匿名的相似改动造一组复用结构题。记录可编译状态、项目约定、所需上下文和应该接受的解释。分别跑启用与不启用该规则的两轮审查。

完成标志　同一组判分标准能区分真实重造、合理新增、上下文不足。保留两类误判并说明原因。

第 4 步

把规则带回真实工作，再决定下一步

项目约定随代码变化。循环需要一个人愿意维护这些出处和例外。

展开可复制的提示词
在一个低风险 PR 上使用该规则，只提交可验证评审意见。请维护者记录反馈并更新例子。下一轮区分规则漏项、查找不到证据和模型误解，决定是否要继续扩充数据。

完成标志　维护者能溯源、接受、纠正 1 条具体意见。若无额外质量收益，先不把训练效果当作已成立的事实。

第 1 节

会写代码以后，还得知道团队为何挑另一种写法

Douglas 说，他提交 Rust 改动时，即使自动评审给了满分，仍有可能收到同事的异议。团队可以从能找到前后文的评审开始，看看同事引用了哪些已有约定。

回看这一节 · 01:59:06 ↗

编译器对遵守语法、类型和构建条件提供证据。团队专家评审还能指出存在类似实现、接口有维护习惯，或者这个变更会把两个生命周期绑在一起。若两份意见发生分歧，先问它们各自用的证据。如果自动审查只能访问局部差异，找到通过结果也没有机会评价仓库中别的设计。

第 2 节

用标签留下推翻建议的证据

“推回”这个标签先帮团队定位到一段会话。真正能复用的是被推回的决定、相关代码，以及同事给出的理由。

回看这一节 · 02:03:04 ↗

讲者在 Paper 控制台找 pushback 片段，关注正在使用 Go 或 Rust 的同事为何开始质疑结果。标记用于缩小搜索范围。事后还要读改动前后的动作，判断一句“这样不行”是因为选择重复，还是因为当时没有说出真实需求。确认后可以写下正确替代方案和适用条件。

第 3 节

会话里有 PR 页面没记下来的判断

如果团队已经在命令行里先审一轮，收集材料的位置也要前移。找一个例子，同时看会话、最终评论和合并后留下的改动。

回看这一节 · 02:06:07 ↗

GitHub PR 留下的是准备交付的内容，工程师在命令行和运行环境里已经调整过的方式，也许只存在于更早的会话。反过来，PR 才能看到最终哪些意见进入了交付。两种来源适合互相查证，权限由项目维护者明确。讲者区分开源 Tapes 与内部 Twin Reviewer 时，具体举出了资料敏感这个理由。

第 4 节

先做 Skill 和评测，再决定训练带来的收益

写 Skill 时选容易举出成功与失败例子的规则。之后才能把新评审跑在留出的 PR 上，由熟悉项目的人确认建议是否有用。

回看这一节 · 02:08:36 ↗

对团队来说，先设置一个工程评测更容易解释投入。拿同样的场景对照已有提示、加仓库约定和加实际例子三种条件，保留哪些情况下仍会误判。如果评测失败只是因为没给评审者看最关键的接口实现，先补检索条件。演讲提到微调和偏好优化，属于当时尝试的一条路；内部实验需要可重复比较，才知道训练是否解决剩余痛点。

练习

用这一讲的方法做一次小练习

实作。从两个已处理的 PR 里提取一次值得复用的人类评审判断。

展开参考答案

记录代码位置、被否决的选择、理由、采用的修改和验证。删掉不需要的私人或生产信息，再把其中一条写进 Skill，留另一条测复用。

实作。建立一组样本比较自动评审与团队评审建议。

展开参考答案

对每个样本写下应该提醒的问题、支持证据和误报条件。分别用通用检查与团队 Skill，统计人复核后采纳的建议和漏掉的要点。

理解检查。代码能编译，为何还会因为重复实现被退回？

展开参考答案

编译告诉人语言层面能够构建。团队还需要检查这段实现是否遵从已有 API 和服务边界，是否引入未来要重复维护的功能。

理解检查。什么时候使用会话轨迹比只读 PR 评论更有帮助？

展开参考答案

当同事在命令行先向 Agent 反馈时，会话保留原始选择、人的理由和修改过程。PR 页面可能只留下最后一次提交。

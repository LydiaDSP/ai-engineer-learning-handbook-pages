Factory 怎样把一次性 Missions 做成持续运行的 Workstreams？

从接收缺陷信号、编排 Agent 和逐步放权，到用合并后的补救记录验证改动质量。

Factory · 核心 Agent 团队（演讲自述）约 15 分钟演讲中文导读与讲解 · Lila
持续交付多 Agent 编排人工检查点
导入

一条缺陷报告怎样持续进入交付流程

假设客户在 Slack 说导出文件打不开，Sentry 同时记录了同一类报错。Factory 的 Workstream 可以定时检查既有信号，关联到已有工单，把重复信息并进同一份待审规格。负责人先确认范围和验收条件，执行 Agent 再开 PR，随后跟进评审、评论和 CI。

Luke Alvoeiro 用这个流程解释渐进放权。负责人可以先让 Agent 收集证据和提出规格，再看每个停下来等人的节点能否放开。合并之后，回退、热修复和新报错也会回到这条流程，供团队判断哪一步需要调整。

上手

把一类重复的 CI 失败接进 L1

选一个测试仓库，拿三条历史记录模拟一次 Workstream。两条记录来自同一提交、同一个测试和同一次失败的重试，第三条来自同一个测试的不同报错。指定一位负责人，先请 Agent 归并线索、提出规格，再由负责人决定是否开 PR。

  1. 写清长期目标。每周减少重复出现的测试失败，只接指定 CI 作业的信号。写明仓库、日志范围、负责人，以及何时暂停。
  2. 保留证据。记录作业链接、提交、测试名和失败特征。把重复的重试归到同一条记录。对第三条记录保留单独的待核线索，请负责人确认是否同源。
  3. 逐步签字。让 Agent 给一份含预期行为、拟改范围和验证步骤的规格。负责人检查规格、PR 和合并前证据三个节点。改动只在测试分支演练。
  4. 保留结果。写下改动所对应的提交、测试结果、观察窗口，以及观察期内有无回退、热修复或补救。把一条可复用的判断写进共享指南，并附来源。
通过标准

第二天换一个人接手。对方应当能找到原始信号，理解为什么归并或分开，知道人工检查停在哪一步，并能复跑一项验证。

复盘

一次性项目和持续维护，需要不同的交互

Missions 适合目标清楚、可验证的大迁移或大功能。用户先与编排器对齐计划，批准后交给 Agent 持续执行。Factory 从使用反馈中发现，很多日常工作一开始很难规划完整，执行过程也需要追问和调范围，而旧流程给用户的介入入口很少。

每个里程碑都加上挑错式审查，可能扩大范围。讲者举了一个从约 60 项扩大到 200 多项的 Mission，时间和 token 随之增加。另一个问题是经验留在单次 Mission 里，后续任务难以接着用。Factory 一方面改了运行框架和环境，另一方面把长期目标、共享记忆和可调整的人工检查点合到同一个 Workstream。

编排

给持续工作一个目标、一组 Agent 和运行环境

Workstream 持有长期目标、身份、运行环境和记忆。它开始可以沿用发起人的身份。工作扩大后，可以迁到由组织控制、持有独立凭据的服务账户。Factory 还用可复用的沙箱配置准备代码库、工具和依赖，让不同 Agent 有各自的执行空间。

编排器将工作委派给负责对应范围的 Agent。Agent 在完成、受阻或发现会改变计划的情况时汇报。人可以继续与编排器对话，也可以为同一项工作接入定时或事件信号。共享文件系统保存调查结果，团队把能复用的判断写进有版本的 Skills。

放权

负责人每次只决定要不要放开下一个检查点

讲者以两条 Slack 频道的缺陷报告为例。编排器可以定时收集报告，参照 Linear 工单或 Sentry 告警去重，再依据长期目标初筛。负责人看到的是带线索的规格，仍来得及调整验收条件。规格获批后，执行 Agent 再推进 PR 和 CI。

演讲里的 L1 在规格、PR 和合并前停下来等人。图中的 L2 放开了规格确认，PR 审查和合并仍由人负责。L4 默认自动合并。负责人可依据一段时间里提议的准确性和合并后表现决定下一个检查点是否值得放开。练习里先保留三个检查点，连续记录哪些提案被负责人改过、为什么改。

验证

把合并后的补救也计入质量

Factory 在 PR 上配代码审查、安全审查、专门的 QA 和预览。审查讨论处理完后，风险裁判可读取精确差异、检出该分支并构建测试，采用主分支上的评审政策。团队还回看作者采纳的审查意见，以及合并后出现的回退、热修复和新报错，将它们关联回 PR。

讲者用「无需补救的合并率」衡量产出质量，即合并后无需回退或再做修复的改动占比。他报告了 Factory 自用案例，包括一周在开发分支交付约 800 份 PR，其中 99% 由 Droid 编写。这组数字记录了产量和作者构成。讲者另用示意曲线说明 L4 的放权门槛（03:55:29）。要比较合并后质量，可以另按可比任务类型和观察窗口记录后续情况。

练习

用三个问题检验 Workstream 的设计

一个失败作业被重试两次，哪些记录应放在一起？

展开参考分析

检查它们是否对应相同提交、测试和失败特征。把同一次失败的重试记录附到同一条线索。出现不同报错时保留独立证据，等待进一步确认。

最近几份规格无需修改，下一步可以怎么试？

展开参考分析

在相同类型的小改动里试着放开规格确认这一个节点，继续保留 PR 检查和合并前批准，记录误收信号、漏收信号或需要返工的规格。发现稳定性变差时可以恢复这个检查点。

这一周合并更多 PR，要补看哪些数据？

展开参考分析

在事先约定的观察窗口里，按任务类型记录可观察的合并数、回退和后续修复。标出仍在观察的改动。这样团队才能讨论产量增加后，质量是否也达到了预期。

原型做得越快，越需要知道该选哪一个

从 Antigravity 的任务协调、插件和管理界面，看产品判断如何进入每轮迭代。

Google DeepMind 软件工程师约 13 分钟演讲中文导读与讲解 · Lila
产品判断Agent 界面快速原型
导读

原型做完以后，才知道哪一步值得做深

同时运行多个 Agent 时，用户返回界面，通常只想知道有没有任务要自己决定。给每条任务铺开完整过程确实能搜到更多细节，但如果用户必须逐条读日志，界面已经把寻找重点的工作转交给了他们。Ishaan Dey 在 06:17:46 前后谈到管理多个任务的界面，用这个问题解释 Antigravity 团队怎样选择展示内容。

他提出先做几个可用的方向，亲手试过，再选一个深入。原型越容易做，这个步骤越划算，但各方案需要回答同一个问题，用户才能判清哪一个更合适。本篇用一张模拟的协作看板贯穿练习。你会把两种界面放进相同的任务，而后写下一份别人能复核的产品决定。

读完可以做什么
  • 用一句话写清用户这一屏要做的决定，再准备多个有可比性的原型。
  • 把 Agent 需要人批准、可以后台继续、已经阻塞的状态用不同证据呈现。
  • 为一项已有的自动化约束做受控实验，判断新模型能否接手排程。
上手

给一张任务面板做两版原型，并用同一组任务试玩

教学场景设为编辑部的任务看板。六条任务分别处于运行、等待材料、等待编辑选择、完成、已暂停、工具错误。练习使用合成数据，每一步最多验证一个问题，做完后只需交付两张原型、一份试用记录和一条决策。

第 1 步

先写用户要做的决定

把“这个面板太复杂”收束为清楚的动作，避免原型漫无目的。

展开可复制的提示词
我在编辑任务面板上要找出唯一一条需要我确认选题的任务。请给出六条合成任务的状态、最后一次变化和完整过程。让另两条任务也看起来很紧急。冻结这份任务卡片，后续原型都用同一份数据。

完成标志　获得一份具有客观答案的测试材料。测试参与者可以凭卡片证据说明哪一条在等人工决定。

第 2 步

生成两版可走通的界面

同一套任务和操作入口让差别集中在信息呈现。

展开可复制的提示词
用这份测试材料做两个能从总览打开详情的 HTML 原型。A 在总览显示最近三条事件；B 用最新状态、需要谁做什么和更新时间概括，日志放进详情。两版排序、标签措辞和跳转能力一致。

完成标志　两版用相同任务编号，能打开同一份详情，只有总览信息量变化。

第 3 步

录下选择过程

第一次点错比最后一句“喜欢 B”更接近使用时的困难。

展开可复制的提示词
写同一句试玩任务，请同事分别找到需要自己作决定的卡片。交换 A 和 B 的试玩顺序。记录首次点击、决定用时、依据和明显困惑，保留反例。不要由我解释界面。

完成标志　每条记录都有任务、原型版本、所选卡片、用时和证据。一位同事的结果会标明只是一次观察。

第 4 步

写一条可以重开的决定

给结论留出条件，模型和任务变了以后才知道何时重测。

展开可复制的提示词
根据试玩记录写一页决策备忘。列出哪版更容易找到需要人处理的任务，哪些任务仍需先看细节，下一轮只改哪一项。列出一条能推翻现在选择的新观察。

完成标志　决策明确指向某个原型、实际证据和需重测的条件。

第 1 节

把部分判断放到原型做出来以后

原型能让团队尽早观察用户怎么操作。讨论投入多少工程时间之前，先决定每个版本能回答什么问题。

回看这一节 · 06:09:28 ↗

把设计判断往后挪，需要把第一轮交付物改成能获得反馈的物件。比如，可以点击的任务面板能暴露一个原先没讨论过的问题，等待后端重试的任务也显示为“待处理”，用户会不会误以为要自己催办？做成静态效果图时，团队容易只讨论颜色。把这项动作做成可试玩的原型，再比较信息位置。

第 2 节

模型变强会改变协调方式

先标出产品帮模型代做的判断，再用真实任务验证哪些决定可以交回模型。用户需要知道任务状态，也需要能干预重要决定。

回看这一节 · 06:11:09 ↗

早期的 Agent 队列适合把工作拆成几条人能盯住的命令。模型能够并行时，卡在排队系统后面的新信息可能会延迟整个安排。与此同时，有些变化是给正在执行的任务补充约束，有些变化是在取消旧目标。异步允许系统早点收到意图，界面仍需要让用户看清楚哪些任务在继续，哪些已经暂停。

第 3 节

让用户自己试出新用法

个人工作流适合先作为扩展存在。团队需要看清哪些习惯只在局部有效，哪些可以提炼为其他用户也认识的功能。

回看这一节 · 06:15:43 ↗

可扩展性为不知道会出现什么需求的团队提供了另一种反馈通道。演讲举了汇总反馈看板、设计演示协作工具和团队自己的插件。每种工具都能先把某个工作流走完整，再判断值不值得加入公共入口。记录哪些角色在第二次、第三次还会用，比插件首次展示看起来全面更能说明它能否留下。

第 4 节

先弄清用户在界面里要做什么

多任务管理界面的读者正在决定接下来该看哪一项工作。可以用完成这项判断所需的时间，来衡量界面的改动。

回看这一节 · 06:17:46 ↗

回到教学看板。版本 A 主要显示“读取反馈、等待审批、已发起重试”等操作历史；版本 B 把“待你选择选题”放在任务标题旁，下面只保留最后变化。你拿到的正确卡片是 C。若测试员先点工具报错的 F，再点 C，误选就暴露了一个具体问题。F 的视觉提示可能抢过了“谁要处理”的标记，下一轮可以只调整这两类信息层级。

第 5 节

先发散，再挑一个方向做深

一轮迭代可以结束于一个选择。留下选择依据，下一轮才知道是在推进方向，还是在重新打开已回答的问题。

回看这一节 · 06:19:54 ↗

三个方案能跑通以后，团队还需要判断原型值不值得承担长期维护。内部任务看板可以用日常任务继续试。如果需求确实跨团队出现，再检查审核规则、权限和术语是否可以统一。在部署一个更省事的界面之前，留下具体证据，说明哪种决定变快了，以及哪些人依然需要另一种视图。

练习

用这一讲的方法做一次小练习

为多任务 Agent 看板写一条能观察到的改进指标。

展开参考答案

给三位读者相同的五条任务，让他们在旧版和新版里指出最需要介入的一条。记录所需时间、选错次数和他们依赖的状态信息，再决定默认界面应展示什么。

为什么早期 AI 工具需要按队列逐条交付用户意图？

展开参考答案

小步提交适配当时的模型和轮流交互。长任务和异步执行普及后，可以试验提前接收意图，检查系统能否清楚说明将立即做、委派或稍后做的工作。

如何决定一个内部插件是否适合成为产品功能？

展开参考答案

观察谁在用、原工作流卡在哪里、多少不同团队有同一障碍。从已有插件提取最小通用能力，找新用户验证，再决定是否放进产品主流程。

已有一个能跑的原型，可再试哪两种方案？

展开参考答案

例如给多任务看板各做一版细节优先和状态优先的原型。统一测试任务，先比较读者能否找到阻塞项，再观察他们查看细节的频率与原因。

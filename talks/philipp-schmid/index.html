导入

两套框架都通过测试，怎样选？

节选版 · 开场音频缺失。现存可听内容从主回放 02:21:16 的一句话中途开始。正文从这里读起。大会官方节选 ↗

Philipp Schmid 每隔一段时间重搭一次编程 Agent 运行框架，问自己哪些工具和提示仍然有帮助。他在这次演讲中比较了专用文件工具、单一 Bash 入口和带媒体查看的配置。即使几套配置完成的任务差不多，走过的轮次、花掉的 token 和等待时间也可能不同。

路径

给同一项任务两种工具接口

讲者先用后训练来解释为什么不必规定每一步。模型可以在环境里选工具，最终产物由验证器评分。同一个仓库改动，可以拆成多次读取和编辑，也可以由模型写一段脚本合并处理。

在这次演示中，逐项调用工具的路线约十轮，组合操作的路线约两轮。这是单项任务的对照。设计自己的评测时，先固定验证标准，再比较两种接口走过的路径。

工具

先确定哪些能力必须保留

在 Schmid 的实验里，Bash 可以把搜索、批量编辑和检查放在同一次调用里。长时间运行的进程仍要有日志和可查询的状态。涉及截图的题目则需要能把图像呈现给模型的工具，把 PNG 作为终端字节读出无法完成这一步。

工具数量可以变，能力要求仍由任务决定。先写下任务需要读哪些输入、改哪些文件和跑哪些验证，再比较哪些功能能由现有接口组合完成。

评测

得分接近时，把耗时和成本一起看

Schmid 用约 350 个编程、知识工作和终端任务比较四套框架。几套配置的得分相近，但 token、缓存命中率和每任务成本有差异。他说每题只跑过一次，小幅分数差异可能来自波动。

记录每次运行是否通过、模型调用轮次、工具调用次数、token、耗时和成本。复跑失败案例和边界案例，查看节省来自减少往返、缩短工具输出，还是任务本身变了。

模型

同一套工具在不同模型上要重测

演示里的 Flash 常把 Bash 当成一次做一件事的工具，逐轮读取和写入。Carbon 在该任务中把查找与修改组合到较少的工具调用里。框架简化能省多少取决于模型会怎样使用接口。

演讲最后讨论了 Code Mode。结构化工具结果可以供脚本继续处理，受控接口也方便记录和审核实际操作。对比两套框架时，给两组相同的权限范围与审批条件，免得权限差异改变结果。

上手

在两份相同的本地测试仓库跑一次对照

建立一份小型示例仓库，包含一个格式化函数、两个调用文件和几条能独立运行的测试。任务是给函数改名并同步所有调用。验收时检查测试结果、旧名字是否仍出现在可执行代码里，以及是否意外修改了其他文件。

  1. 固定条件。复制同一个初始提交，使用相同模型、任务描述、时间预算和文件权限。
  2. 只换工具接口。A 组使用专用查找和编辑工具。B 组用一个限于测试目录的终端入口；两组都能运行相同测试。每组至少跑三次，每次重置数据。
  3. 记录通过和代价。每次记下通过状态、模型轮次、工具调用、token 和秒数。应用同一套测试，保留失败和超时记录，再用一个没参与调整的样例复测。

记录模板。配置 A／B、运行编号、通过状态、模型轮次、工具调用、token、耗时、失败原因。

练习

三道题检查这次比较是否有效

两组都通过，B 的平均轮次少一半，可以看出什么？

在这组样题与设置下，B 的模型往返轮次较少。继续核对 token、用时和失败率，才能知道这个差异是否带来整体收益。

如果任务还要核对改完的界面截图，该怎样改实验？

先给两组同等的截图查看能力，再比较剩余的工具差异。也可以把纯代码任务与截图任务分开统计，查看结果是否因输入类型而变。

换了模型以后，能直接沿用原来的结论吗？

用新模型在同一批题上重复对照，并观察调用轨迹。新模型批量处理和理解工具输出的方式可能不同。

导读

当页面能跑起来，开发者还要看哪里？

Syntax 的午间节目从一条找隐式状态机的提示开始。加载中、完成和出错被写成三个互相独立的布尔变量，界面却可能只允许一个状态可见。程序编译通过也没有阻止两面同时出现。两位主持人借这个具体问题继续聊桌面应用重写、代码审查擅长发现什么，以及生成界面怎么用人能复查的方式评价。

这场没有一条适用于所有项目的工程规定。更实用的读法是把对谈拆成三次可独立练习的观察。先读结构，再读迁移证据，最后读用户实际体验。这样学习，看到某个工具顺畅跑完一次，就能知道还需要补哪一类观察。

读完可以做什么
  • 用事件和允许迁移描述一个页面的隐式状态。
  • 比较桌面实现时同时记录资源、兼容性和可重复的行为检查。
  • 用相同题目与用户任务比较生成界面，避免把风格猜测当评测。
上手

把一个生成页面从“看起来行”改到有具体证据

选一个有加载、完成和失败提示的小页面。用本地测试数据检查，避免改真实用户数据。先保留当前实现，两次实验都从同样输入开始。

第 1 步

写下哪个画面可以同时出现

散落的开关很难让人读懂所有组合。

展开可复制的提示词
列出加载、成功、失败和重试之后的实际显示，把每个可以触发变化的事件写下来。找到一个界面允许冲突显示的案例，提供最短的重现。

完成标志　读者能从一个事件跟到一次屏幕变化。每个状态组合有明确结果。

第 2 步

让表示方式本身约束状态

为每个新分支加条件不一定消除冲突。

展开可复制的提示词
提出一个使用单一状态或清晰状态转换的最小修改。保留现有产品预期。在本地测试里覆盖两次并发请求，以及先失败再重试的顺序。

完成标志　同时出现加载和成功的冲突能被检测；重试时恢复到预期状态。

第 3 步

查 DOM 与视口适配

分数和截图只说明了仪器观察到的一部分。

展开可复制的提示词
比较桌面与手机尺寸下相同动作的 DOM 和键盘顺序。查找是否重复渲染、焦点是否停进隐藏分支。保留两种宽度的截图和实际操作记录。

完成标志　重复结构有直接证据，判断覆盖了键盘或辅助技术的一项实际路径。

第 4 步

让两份生成品经同一套流程

模型名称与配色印象可能干扰评审。

展开可复制的提示词
把两份生成结果去掉来源信息，统一测试相同任务。先检查按钮范围、异常反馈和移动端，再记录视觉判断，最后同时给每份产物指出一处好与一处具体改法。

完成标志　每项意见能回到任务或实际观察，而非根据风格猜厂商。

第 1 节

从布尔标记里找出隐式状态机

选一段加载逻辑，先把已有状态写出来，再看哪些组合根本不应该出现。让 Agent 帮忙找位置，开发者负责定义迁移规则。

回看这一节 · 04:11:43 ↗

教学推演。假设页面发起搜索后，用户立即换了条件。第二次请求先成功，第一次却晚到并失败。若两个结果都能各自设置 success 或 error，就可能叠出旧错误。把每次请求和当前状态绑定，检查晚到结果是否仍属于正在追踪的那一次，才能看出问题并确认修复。

状态表还可以让人问出“哪一步应该取消”的问题。譬如用户离开页面后是在后台保留搜索，还是立即结束？主持人讨论的是状态集中本身，取消策略则需要产品另作决定。把这两项拆开以后，Agent 可以先画出当前行为，决定权仍留给能解释异步结果用途的人。

对照做法时也要看事件有没有一次性副作用。将页面从“失败”重置到“等待”之后，已经发出的请求与提示条是否还被保留，需要用一次真实操作确认。变更只有单一枚举而没有检查事件顺序时，晚到结果依然可能覆盖当前页面。

第 2 节

用文档、样例和确定性校验支撑陌生工具

切换框架可以先做一段真实流程。把示例和错误信号一起交给 Agent，再观察它能否在看不到标准答案时从错误中恢复。

回看这一节 · 04:18:54 ↗

节目中另一个例子是多处读写文件的 CLI。把文件访问归给同一个模块后，工具还可以检查新代码有没有绕开它。与状态集中相同，设计给后来的维护者留下一个能找到的入口。文档可以说明怎样走，lint 与测试能更早报告走错路径；两者不用承担同一份工作。

主持人把 FoldKit 组织状态和 Elm 类比，也提到早期给模型补 SvelteKit 资料的经验。练习中可以选一个相同的小改动，用候选框架各走一次。先查文档是否与当前依赖版本相符，再给一个官方例子，看类型或框架诊断是否指出错误所在。目标是评估维护时的反馈，节目里的顺畅演示不足以推断团队长期维护成本。

假如某个新栈提供面向模型的说明，先把真实项目中反复出错的一种操作写进对照，例如怎样搬一段状态。观察新加入的维护者与 Agent 会不会都去到正确文件。这样的测试能够发现目录和说明里的信息缺口，也保留了它们分别读到哪些线索。

第 3 节

重写桌面应用要查的不只有内存

移植技术栈时，先列旧版本给用户的体验，再找跨平台重现的方式。一次本机演示只能提供一部分答案。

回看这一节 · 04:28:12 ↗

讨论桌面应用时，他们看到一个关于 Discord 的内存截图，也谈到了 Electron 与系统 WebView 的差别。他们还聊到 Rune 一类 GPU UI 框架及跨平台渲染的不同取舍。是否值得迁移需要看其他用法。跨平台分发因为少打包运行时而变轻，也可能增加系统差异带来的兼容成本。读这段时可以把节目里的观察、自己能重跑的试验、仍没有可比数据的事分开。

桌面迁移的例子可以从安装后的一个首用动作开始，比如保存设置再重启。旧版和新版在同一应用状态下分别重放，可以留下窗口错误提示、焦点、保存结果。同一套任务若在另一系统上失败，先记差异，资源占用仍单独报告。主持人对旧测试迁移的疑问就在这里，不能只搬过去断言语法，失去断言对应的用户行为。

第 4 节

留住能看出问题的知识

技能盘点可以从上一次评审开始。问团队是靠什么看出坏结果，再决定哪项知识值得继续练。

回看这一节 · 04:34:43 ↗

节目里桌面和手机各渲染了一份完整 DOM，光看页面外观很难发现。可以让 Agent 标注主要区域在 DOM 中出现几次，再用键盘逐个聚焦。若隐藏结构没有被移出焦点序列，真实操作会撞见多走的一组步骤。合并到同一结构时，要保留变化前后各一段证据，便于检查响应式布局没有被一起抹掉。

第 5 节

用盲看练习观察产物

判断一个界面可先遮住模型名。按需求、层次和完成任务的难度检查，再看自己对这些结果的判断会不会受标签影响。

回看这一节 · 04:43:05 ↗

猜模型是一个有效的现场小游戏。它把颜色渐变、排版和输出边界变成观察对象，但样例数、题目数和人的先验都限制了比较。可复用的方法是先让评审写下实际看见了什么，再核对提示和用户任务。比如原要求是一个可以触发提交的按钮，却出现多个额外对象，评审可以先记范围偏移，之后再谈整体好看与否。

第 6 节

让用户在实际使用中感到被照顾

发布前挑一个常被忽略的小环节。让新用户从打开应用开始，试到能完成自己的目标，记录哪步需要猜。

回看这一节 · 04:51:26 ↗

Rex 的更新提示是讲者用来说明细节的一个落地例子。改进前可以先给人一组真实问题，让他们判断现在是什么版本、要不要升级、怎样得知升级完成。若交给 Agent 做同样的展示，验收可以记录用户是否看见并理解升级状态，以及怎样处理升级失败。视觉判断放在这条路径里，比对一张漂亮截图投票更能发现细节缺口。

练习

用这一讲的方法做一次小练习

把三个互相独立的页面标记变成一份状态表。

展开参考答案

先列 idle、loading、success 和 error 四个状态，只给合理的迁移，例如从 error 重试进入 loading。确认加载和错误不再被同时显示，并用测试覆盖每个出口。

为什么有了文件管理器，还要加 lint 检查？

展开参考答案

抽象说明预期路径，检查阻止后续代码绕开路径。可以规定直接访问仅在文件管理器内允许，并保留一条反例测试，验证约束确实生效。

从两张生成图可以学到什么，怎样进一步做可靠比较？

展开参考答案

两张图适合观察具体差异。要系统比较，就统一任务、资源和评分标准，重抽多组样例，隐藏模型名，让评审先看是否满足要求再评美观。

选择一个已有的个人应用，做一次发布前可用性检查。

展开参考答案

请没看过代码的人按说明安装并完成一个真实任务，记录第一次成功的用时。观察错误消息、默认值与更新提示，再挑最容易卡住的一步改。

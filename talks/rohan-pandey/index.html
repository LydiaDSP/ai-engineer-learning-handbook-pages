导读

服务变快了，还是只有统计口径变了？

Rohan Pandey 展示一套用于搜索模型服务参数的工具。操作者先提供一份能跑的配置，Optuna 根据已有试验的结果选出下一组参数。它的直接好处是把枯燥的重复试验交给工具，实验的人仍要决定怎样才算赢，以及算力可以花到哪里。

同一套配置可能让短聊天更顺畅，同时让长上下文等待更久。演讲把短聊天、长聊天、检索增强和分类分别纳入请求形状。学习时可以先把自己的一个请求场景量清楚，再看怎样设置预算、保留基线和复跑获胜配置。

读完可以做什么
  • 说明哪些硬件、模型和请求条件需要保持一致。
  • 给吞吐加上等待和错误限制，把有效生成量与原始吞吐区分开。
  • 读懂 HTML 报告与 YAML 各自可以交接的内容。
上手

在一台可用机器上做一轮小规模配置对照

用已有测试环境跑一组不涉及真实用户的请求。没有推理服务器时，用三份虚构运行记录演练验收。预算和停止条件在比较前定下来。

第 1 步

写下一类请求的实际限制

请求条件会决定哪一种配置被选中。

展开可复制的提示词
用测试请求确认输入和输出长度、并发、预热方式、可接受的响应等待及错误率。写下基线配置、模型版本和设备。

完成标志　固定模型与负载，观察者可以用同一条件复跑。

第 2 步

给候选参数设边界

搜索应当比较配置组合，预算耗尽后可以有据可查地停下。

展开可复制的提示词
只列两个可安全在测试环境修改的参数。为每个参数给出可选范围、固定参数和总轮数。除非能写清收益依据，否则不要追加试验。

完成标志　每轮结果对应一个确定配置，机器容量与停止规则明确。

第 3 步

先拒绝越过服务承诺的结果

输出 token 多并不说明用户获得了可用的响应。

展开可复制的提示词
并排读基线、候选的吞吐、等待和错误。根据预先约定的条件排除不可接受方案。为排名最高的一项写出它不适用的负载。

完成标志　即使它的原始吞吐最高，超出等待限制的配置也会被淘汰。

第 4 步

用导出的 YAML 做重复实验

一轮峰值可能受预热、负载波动或噪声影响。

展开可复制的提示词
保留基线与获胜配置，将两者放到同一环境再跑。保存原报告、两份 YAML 和独立复跑结果。对比结果不同就列出差异，待人决定。

完成标志　重跑证据能区分首次选出来的结果与后来验证的结果。

第 1 节

让 Optuna 根据上一轮结果挑下一组

一个最小试验先要有起始配置和评分方式。每跑一轮，就为接下来挑哪组参数增加一条信息。

回看这一节 · 02:13:39 ↗

贝叶斯优化把已经花掉的试验利用起来，下一轮既可以挖已有好结果附近的参数，也可以试一个信息不足的区域。条件固定后才有可比较的得分；如果负载每轮变化，一个参数组合即使看起来改善，也可能只是遇到了更短的请求。

第 2 节

先固定模型、硬件和负载

换一种机器或者请求形状，配置的好坏可能就变了。调参试验要从能够复跑的负载开始。

回看这一节 · 02:15:45 ↗

教学推演。假设自己规定排队加服务用时必须低于两秒。测试 A 一分钟完成 80 条且都满足要求，B 完成 100 条，只有 60 条达到约定。若讨论目标是在该限制下完成的请求数，A 每分钟有 80 条有效，B 只有 60 条。这只是教学口径，讲者演示使用与 token 有关的有效产出，自己复测要明确分母和时限。

第 3 节

把调参结果留成报告和配置

最佳轮次要能与起点和其他候选相比较。HTML 报告说明差异，YAML 给复跑提供明确输入。

第 4 节

把案例里的提升放回各自试验

两个报告来自不同模型的历史搜索。可以参考搜索过程，并为自己的服务指标另留一轮独立复跑来核对结果。

回看这一节 · 02:18:12 ↗

HTML 报告给出了试验次数、各轮得分和当前领先者，适合查看找到配置的过程。YAML 写的是最后挑中的值，还需要和所用模型、硬件及请求形状一起留档。参加选型的人如果只收到 YAML，日后就无法解释为什么这些参数适合某台机器。

练习

用这一讲的方法做一次小练习

实作。写一份自己服务的最小调参试验说明。

展开参考答案

固定模型、硬件、代表请求、到达率和时延门槛，记下原始 YAML 与基线。预先设定试验次数，复跑排名靠前的配置，比较其尾部时延和有效吞吐。

理解检查。为什么一次较高的总吞吐不足以直接选中配置？

展开参考答案

真实服务还要满足等待时间等约束。生成量上升，超时的请求也可能更多，需要按自己的服务目标计算可接受的吞吐。

理解检查。试验费时小时级，报告与 YAML 分别能节省哪一步？

展开参考答案

报告帮人追溯候选、挑选要复测的轮次。YAML 让后来的人跑相同参数，不用从截图重新抄设置。

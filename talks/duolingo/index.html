Duolingo 怎样让 Agent 写的 iOS 测试走到合并？

挑选值得补测的文件，在开 PR 前运行验证，按状态处理 CI 和评审，再把拒绝原因写回测试规范。

Duolingo · Staff Engineer约 13 分钟演讲中文导读与讲解 · Lila
单元测试CI人工评审
导入

先从更容易独立验证的代码补起

Duolingo 每周发布移动端应用，同时运行大量 A/B 实验。越来越多同事可以借助 Agent 向 iOS 仓库交付代码，团队需要更快确认改动是否符合预期。Kush Agrawal 所在的平台团队选择用单元测试给开发者和 Agent 提供可以反复运行的反馈。

iOS 仓库一半左右已经迁到 MVVM 架构。团队优先补 ViewModel、仓库层和数据源，这些文件相对容易隔离依赖。界面代码留给适合它的快照测试。讲者展示的覆盖率从全库 11% 起步，MVVM 范围约为 9%。后面看结果时要分开两个分母。

上手

用一个小仓库演练补测到评审

选一个已有单元测试的练习仓库。挑一个依赖可以用 fake 替换的模块，找一条尚无测试的失败路径，例如缓存读取失败时返回默认值。记录目标文件、预期行为和现有测试命令。

  1. 定范围。列出可写的新增测试和辅助文件路径；保留现有测试与应用源码。提供仓库中的测试框架、命名和 fixture 示例。
  2. 生成并验证。让 Agent 写一个正常路径和一个失败路径的测试。记录实际执行的命令、通过数量，以及待审差异。必要时在练习分支临时改变被测函数的返回值，确认新测试会失败，然后恢复。
  3. 演练 CI 分支。准备一次格式错误和一次真正的断言失败。格式错误用现成格式工具修复；断言失败先读日志与差异。若任务需要改源码才能推进，记录阻塞原因，交还给负责人。
  4. 交给评审。用同一张清单检查预期行为、文件范围、运行结果与重试记录。让另一位同事复跑一条测试，核对是否应该批准。记录被拒的具体原因，补进下一轮的测试说明。
通过标准

新测试能发现自己声称覆盖的行为变化。评审者能根据命令和差异重现结果，并能看出哪些失败应当停止重试。

流程

先验证可行性，再把五步循环搬进生产

团队把工作拆成五步：找文件、写测试、验证、处理 PR、根据反馈改进。最初用本地 Claude Code 命令编排 Xcode 覆盖率报告、候选文件脚本和子 Agent。两批分别合并 8/17 与 19/40 份 PR。团队借此发现 Agent 会在同一个文件混用 XCTest 和 Swift Testing，也会写依赖计时的测试；随后把规则和例子补进测试 Skill。

生产版由 Temporal 调度任务，S3 在工作流间共享状态，GitHub 负责 Actions、标签和 PR。主分支新生成的覆盖率报告用于挑下一批文件。候选脚本提高 MVVM 组件的权重，降低遗留和大文件的优先级。生成阶段并行运行，PR 模板标明由 AI 生成，方便后续识别和指派。

评审

根据 PR 当前状态选择下一个动作

随着待处理 PR 增多，团队定时扫描带标签的开放 PR，每轮只为每份 PR 做一件事。CI 还在跑或已有评审者时跳过。出现冲突或长时间无人处理时关闭。CI 转绿后，根据被测文件的贡献记录找评审者。人可以批准、修改、改派，也可以拒绝；拒绝后文件进入 30 天冷却期。

CI 失败时先分辨作业类型。格式等 pre-commit 问题优先用确定性工具修复，其他失败才交给 Agent 看日志。自动修复最多尝试五次，仍然失败就关闭。工程师也能在自己的 PR 上加标签，仅对本次改动中的文件生成一份关联的测试草稿 PR。

质量

测试通过后，还要检查它怎样通过

最初 Agent 在 Linux 上生成测试，直到远程 CI 才遇到 Xcode 和 SwiftLint 检查。团队改善规则示例、加自动修复，并迁到 Mac 运行器，在开 PR 前先构建和检查 lint。环境越接近实际构建链路，部分问题就越早暴露。

评审前还经过三层质量控制。先按文件范围关闭越界改动，再处理已有审查工具的最高优先评论，最后用专门的裁判检查生产代码改动、已有测试被改动或关闭，以及引入长等待等问题。裁判要留下可读的拒绝理由，团队据此修改 Skill。人仍对每份合入的测试 PR 作最后批准。

结果

分别看覆盖率、合并量和评审成本

据讲者报告，流水线合入 700 多份测试 PR，增加约 22.5 万行测试代码；全库单元测试覆盖率从 11% 升到 24%，MVVM 范围从 9% 升到 59%。这些数字面向不同问题：合并量反映交付，覆盖率反映运行过的代码范围。评审团队还可以看一条测试能否抓到预期回归、反复运行是否稳定、处理一份 PR 用了多久。

团队也把这套循环用于迁移旧代码和生成快照测试。讲者在结尾提出让快速分类器代替 PR 状态机决策树的设想。可以先用历史状态离线比较两种决策，核对误指派、过早关闭和遗漏的重试，再考虑接入实际队列。

练习

判断哪些工作可以自动推进

CI 为绿，但 Agent 为此修改了应用代码，怎么处理？

展开参考分析

按补测任务的文件范围拒绝改动，记录越界路径和对应断言。若验证暴露的是应用缺陷，把证据交给负责人，单独确认修复范围，再补测试。

同一条 lint 错误反复出现，先改什么？

展开参考分析

先定位规则和可自动修复的路径，在开 PR 前运行同一检查。可复现的修复交给格式工具或 Actions。随后把易错场景和正确写法补进测试说明，观察同类失败是否下降。

某个测试靠等待固定秒数通过，评审还要看什么？

展开参考分析

找出等待对应的状态，改为由受控时钟、明确事件或可查询状态驱动。分别确认正常与失败路径，重复运行检查稳定性，并保留评审者可复跑的命令。

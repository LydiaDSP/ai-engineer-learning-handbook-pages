导入

两条规则放在一起，订单会进入哪个状态？

一条规则写着，订单提交时如果缺货，就标成待补货。另一条写着，任何订单都不得标成待补货。把它们交给编程 Agent 前，可以先问一个具体问题。假设顾客现在提交了一笔缺货订单，两条规则要求系统做什么？

Rajath Mahendrappa Kotyal 用这个电商例子介绍 AWS 团队的 Kiro Specification Analyzer。它尝试在代码生成前指出规格里的冲突、歧义和缺口，把需要业务知识的问题交回用户。

形式化

把触发条件和结果变成可检查的约束

把规格里的事实和动作拆出来。用 S 表示订单已提交，I 表示库存可用，B 表示转为待补货。第一条规则可以表达为 (S ∧ ¬I) ⇒ B，第二条就是 ¬B。

把“已提交且缺货”加入当前场景后，第一条要求 B 为真，第二条要求 B 为假。求解器能检查在这些条件下是否存在一个同时满足全部约束的赋值。如果只检查整组规则，求解器也可能找到“订单尚未提交”的赋值。要发现实际业务场景里的冲突，还得把那个场景的条件写进去。

演讲用 SMT-LIB 表示约束。正文保留讲者对求解器结果的口语描述。这里关注的是可满足性，也就是有没有符合约束的赋值。业务规则是否符合原意，还要由熟悉场景的人核对。

解读

对多次形式化结果按业务行为分组

演讲先让模型尝试澄清措辞，遇到难以澄清的规则再把自然语言换成 SMT 表达式。讲者还提出多次翻译同一条规则，观察模型有没有补入不同的假设。

可以用逻辑等价把不同写法归到一组。按前面的符号约定，(S ∧ ¬I) ⇒ B 与 ¬S ∨ I ∨ B 对每种赋值都会给出相同结果。如果一个解读增加了“用户允许缺货下单”这个条件，就需要再问。当订单已提交、缺货且用户未经询问时，两种解读的结果是否一致？找到这样的场景，就能把分歧说清楚。

澄清

把冲突、歧义和缺口交给能决定的人

  • 冲突。同一场景触发了两条要求相反的规则。提交缺货订单时，一条要求标为待补货，另一条禁止标为待补货。
  • 歧义。“移除订单记录”可以指永久删除，也可以指从客户界面隐藏并保留记录。把两种后果写出来，请规则负责人选定。
  • 缺口。闲置订单可能出现，但现有规格没有说应保留、提醒还是取消。先确认什么算闲置，再补上对应动作。

提问时带上一组能触发分歧的输入和各选项的后果。负责人作出决定后，把条件和结果写回规格，用相同场景再检查一次。仍需确认的规则可以暂缓实现。

上手

用一张情形表做一次规格评审

设想你正在写一个虚构书店的订单规格。准备四条规则。

  1. 用户提交缺货订单时，将它设为待补货。
  2. 系统不得把订单设为待补货。
  3. 用户取消已提交订单时，移除这条记录。
  4. 有库存的订单在提交后进入备货。

用纸笔或表格做下列检查。每一行记下场景、触发规则、要求的结果和需要回答的问题。

  1. 填入“已提交、缺货”，列出两条规则各自要求的结果。
  2. 填入“已提交、有库存”，检查进入备货是否与其它结果冲突。
  3. 填入“已提交、用户取消”，分别写出“永久删除”和“仅前台隐藏”的后果。
  4. 增加“订单草稿闲置 24 小时”一行，标出附近的规则是否覆盖它。

为这家虚构书店选定一项明确的决策。例如允许所有已提交的缺货订单进入待补货，就去掉禁止待补货的规则，或者把禁止规则写成有明确触发条件的例外。补齐取消和闲置的规则后重跑这四行，确认每个情形都有可验证的预期结果。

练习

核对三个判断

为什么要单独检查“已提交且缺货”？

只检查整组规则时，未提交的订单可以使第一条规则不触发。固定已提交和缺货后，两条规则才同时要求相反的待补货状态。

“移除订单记录”要怎样改写才便于实现？

明确谁看不到这条记录、后台是否保留、何时生效。例如“取消后立即从客户订单列表隐藏，订单记录继续保留在后台”。保留多久由规则负责人确认。

求解器找到一个可行结果后，还要确认什么？

确认场景和字段覆盖了真实业务，形式化表达没有遗漏原文约束，并且各场景的处理动作符合业务负责人的决定。

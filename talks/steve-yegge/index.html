从 Wyvern 的交付积压看清任务、上下文和人工验收怎样影响软件工厂。

导入

为什么产出更快之后，还是得放慢？

Steve Yegge 为自己维护的角色扮演游戏 Wyvern 搭了一套 Agent 编排系统 Wheelhouse。老玩家和管理员在日常沟通中使用这套系统。按讲者的说法，某段时间它每天产出约 50 到 100 项功能，玩家跟不上阅读和测试，请他放慢速度并给出路线图。

他回顾了此前的 Vibe Coder、Beads 和 Gas Town。Vibe Coder 让他体会到为模型添加太多职责会让系统难以维护。Beads 则保留下来，用于跟踪和关联任务。演讲标题里的「垃圾山」是他用来形容累积到难以维护的项目、规则和记录的说法。

工厂

把产品、社区和交付放在同一个流程里

Wheelhouse 围绕 Wyvern 的工作方式设计。它处理玩家提交的请求，与管理员沟通，并把改动推进到可以检查的阶段。Yegge 说，即使关掉 AI，玩家和管理员也能继续运营游戏，但大家已经习惯让工厂承担一部分协作。

演讲提到合并队列、持续集成和审查是可单独检查的技术环节。任务该交给谁、哪些优先做、谁有权接受改动，取决于团队怎样分工。用这两个视角读案例，可以找出下一项需要改善的具体环节。

队列

用队列找出被产量掩盖的等待

Yegge 用 Beads 跟踪工作和任务之间的关系。他早上先看哪里排起了队、哪些执行者没有任务、哪些工作走在人工批准之前。积压增多时，先确定它卡在安全审查、测试、人工验收还是发布决定。

把新任务交给更多 Agent 会增加推理消耗，也可能继续推高已有队列。除了生成量，还要记录进入待验收状态的数量、完成验收的数量、最早等待的任务，以及检查和返工占了多少时间。演讲中的订阅、算力和 token 估算来自讲者自己的使用情境。

上下文

让临时决定有适用范围和结束条件

演讲里有一个反复出现的问题。讲者随口纠正一次，Agent 就可能把它带进以后会话的规则。当工作记录只能追加时，旧版本和新决定会一起留在上下文里。任务可能因此停在等待或反复确认阶段。

可以给当前规则写明负责人、适用范围和复查日期。规则失效后，在活跃清单里标明替代项，仍可从历史记录回看。开一个新会话时，先给它本轮职责、最近的交接和有效规则链接，再让它开始工作。

交接

如何读懂 Agent 角色的故事

演讲后半用 Lark、Penguin 和 Swallow 等角色讲工作移交。社区角色经常被消息打断，一项需要持续专注的准备工作可以交给另一角色。人类和 Agent 被叫作同一个职位时，会话里的职责说明要能分辨两者各管哪部分工作。

Yegge 用拟人化语言解释日志里出现的反思和自我限制。这些说法是他对自己工作流的观察与解释。可以从角色描述、待处理任务和会话记录里检验具体行为，再看更清楚的交接是否减少了反复确认。

上手

用两轮模拟运行测出队列瓶颈

准备一个本地游戏项目的模拟任务清单。放入五项能单独验收的小改动，给每项写一句预期结果、一个验证入口和一位验收人。用一个纯文本文件或手边的看板记录「待做、进行中、待验收、完成」。

  1. 先测生成快而验收慢。模拟本轮五项改动都准备好，但只够验收两项。记下各列数量、剩余事项和最久等待的一项。
  2. 按验收能力拉取新任务。以同样的起点再跑一轮。允许同时有两项待验收改动，每验收一项才从待做清单补进一项。比较两个方案的完成数和积压位置。
  3. 留下一条能接着做的记录。假设其中一项改动临时暂停发布。写清暂停范围、恢复条件和谁负责确认。下一轮从记录恢复时，检查它会不会拦住无关任务。

按每轮相同的时间段和验收能力做对比。验收计数按证据齐全且已通过的改动记录。练习使用模拟任务和记录。

练习

核查三处常见的判断

第一轮准备了五项改动，只验收两项，哪一步堆了三项？

三项堆在待验收。看下一轮能否让进入该队列的速率与验收速率接近。对比时同时记录完成数，避免用待验收更少直接推断交付更多。

一条模拟发布规则写着「先别发」，还缺什么？

至少写出适用的改动或版本、解除条件、确认人和复查时间。下一班能据此检查哪些工作仍可继续。

Agent 遇到不明确的交接后反复确认，如何检验改法？

固定任务和初始材料，分别给旧交接与明确写出职责和验收证据的新交接。记录追问次数、是否走错流程、能否提交验证结果。用行为差异检验改法。

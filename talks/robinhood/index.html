脚本、Agent 和人怎样分工审数据变更？

拿一条整数列拓宽的 PR，跟着三层审查走一遍，看见注册血缘之外的风险。

Robinhood 数据平台约 28 分钟演讲中文导读与讲解 · Lila
数据平台代码审查人工复核
导读

源表的列变宽了，下游为什么反而可能失败？

Chetas Joshi 的示例 PR 做了两项改动。摄取管道把上游新增的一列带入数据湖，并把湖表中另一既有列从 integer 扩宽为 bigint。已登记的消费者通过检查，Agent 随后在代码里找到了一个未登记的作业。它读取扩宽后的湖表列，却把值写入仍只接收 integer 的另一张表。超过旧类型范围的值会在写入目标表时失败。

这场真正可借鉴的是审查分工。系统能够直接读取的生产事实交给脚本，代码里的线索留给 Agent 追踪，证据与权限不足时由人决定。三层要能互相交接。否则，即使都写了“通过”，也没人能说明三个通过分别覆盖到了哪一部分。

读完可以做什么
  • 从一条字段变更追到目标表和实际消费者。
  • 写出脚本、Agent 和人的输入边界及交接记录。
  • 把漏判、误升级和正常升级分开记录，给审查规则建立回归样本。
上手

给一次字段变更补上审查证据

选一个可以在本地重放的旧 schema 变更。准备脱敏的 diff、人工构造的旧值与边界值、生产环境之外的下游清单。先读记录和代码，练习不用连接或修改生产环境。

第 1 步

把可查证的事实先补齐

变更意图和生产注册情况往往存放在不同地方。

展开可复制的提示词
仅使用提供的资料，列出列类型前后差异、已登记消费者、数据负责人和分类要求。区分每项是通过、失败还是材料未提供。附你查看的快照日期。

完成标志　每项事实带来源，缺资料的单元不会被打勾。

第 2 步

让 Agent 写出读写链

模型能定位仓库里的关系，但不掌握作业实际运行状态。

展开可复制的提示词
从变更字段追到可能的读者和再次写入的表。每跳列出文件位置、读写关系和无法核对的部分。报告准确写明搜索范围。

完成标志　别人可以重查每次引用。搜索未发现与生产没有消费者区分记录。

第 3 步

把风险交给有权限的人

人需要的是一个可行动的问题和材料。

展开可复制的提示词
根据发现拟一条升级消息。写出兼容问题、可能的失败输入、受影响位置、需要负责人确认的事实以及建议的部署先后。不要更改任何数据或权限。

完成标志　信息足以让负责人决定先改哪处；涉及生产的判断仍有具名责任人。

第 4 步

用旧改动训练审查流程

只看通过率会掩盖两种不同的错误。

展开可复制的提示词
用一份正常扩宽、一份目标保留窄类型和一份消费者未知的案例回放规则。标出漏掉风险和错误升级的案例，分别记录下一项改进与预期。

完成标志　除了正常放行，还有一个应真实触发的反例与明确的资料缺口。

第 1 节

一条看起来无害的列类型变更

Chetas Joshi 用同一条 PR 串起整场。它将上游新增的一列同步进数据湖，同时拓宽湖表中另一条既有整数列。登记过的消费者可以接收扩宽后的值，剩下的问题要沿读写链继续查。

查看直播片段 · 04:54:42 ↗

CI 拿到什么信息决定它最适合检查什么。只要登记表与仓库里真正的读写链有差距，“已检查的作业都兼容”就无法覆盖尚无登记的作业。读这场时先写一条能接受的签字措辞。例如“库存表增加可接受的值域，已核对注册消费者，下游实际执行状态仍由数据负责人确认”。一行摘要能保留结论范围，后续的人就不用倒查当初批准的是哪项承诺。

第 2 节

先从权威系统查明事实

对目录、注册表和环境里能直接回答的问题，用确定性的检查留证据。某条确定性规则失败时，模型的解释不会让它变成通过。

回看这一节 · 00:06:47 ↗

在原案例里，schema registry 核对新增列是否已在上游登记。对于另一条被扩宽的湖表列，血缘检查核对已登记的下游消费者。目录还负责核对所有者和个人信息标签。

脚本的优点是重复性。在测试环境用近似规模的数据验证新鲜度，就能观察管道是否在要求的窗口完成。但一次通过只能支持这批输入、这个环境和这些已登记依赖。记录范围后，下一层才能在剩余的问题上工作，不必重新猜测脚本做了什么。

把新鲜度也放进脚本检查，意味着数据正确与按时送达分开验收。一个变更不会改行值，也可能使处理时间延长到当日任务错过窗口。教学中可以保留同样规模的测试输入，比较任务是否跨过预先定义的完成条件，记录测试时的环境和实际耗时。当前本地测试的表现无法代替对生产运行的最后确认。

第 3 节

从仓库补出登记漏掉的一环

这一层的价值是寻找线索并讲清后果。代码里找到的消费者要交给人去确认是否仍在生产运行。

回看这一节 · 00:10:22 ↗

假设本地复制了一个简化案例。旧值能写入 A 和 C；A 类型变宽后，新的大值仍能写进 A，读 A 的 B 作业把值写入 C 时却失败。把 A、B、C 三个点画出来，就能看到原来的 schema 测试只站在 A。回放还应包括可以跨入新值域的输入，避免测试数据碰不到问题。

调查下游时要看读取后还做了什么。若 B 只是用于报表展示，需核对显示或接口可接受的值；若 B 还给 C 写值，目标类型与兼容性就是额外检查。去验收时把两个消费者分开，即便同在一个仓库也有不同的失败模式。演讲的重点是找到证据链、再由业务和运营确认它是否覆盖实际路径。

第 4 节

哪些变更交给人，交接什么

送审时把风险路径和缺失事实随评论一起交过去。需要人决定的问题，即使模型判断很有把握，也会留给相应负责人。

回看这一节 · 00:15:01 ↗

一个有用的升级记录可以短到只有三部分。先描述“修改后的源列允许比原类型更大的值”；再放仓库里的读写引用和需要的环境；最后问“B 仍在生产么，如果是，C 什么时候可以先拓宽”。对方能据此决定部署顺序。把报告写成“有风险，请复核”，人仍需从头找问题，审查回路会把工作转移到下一个人手里。

有人问到数据权限时，把证据和授权人分栏。模型找到存在读权限的线索，也只能提示查哪份规则，不能代替有权限的负责人授予真实访问。一次升级是否恰当，要看发往了谁、给了什么证据、未核实内容有没有保留。

第 5 节

谁来审审查器

团队同时记下危险变更漏掉和正常变更被误拦。两种错的修法不同，练习也从这里开始。

回看这一节 · 00:18:04 ↗

讲者报告的漏判约 2% 属于团队当时的审查记录，他没有给出同口径的单一误升级率。更适合复制的是反馈方法。人留下为什么不同意的说明，值班工程师把有重复性的失败转成规则。加密字段的例子也提醒团队，规则应描述实际转换与分类条件，不能只记住某个字段名称。

讲者报告，截至 2026 年 8 月 31 日，约 60% 的数据管道 PR 无需人工评审即可合并，人工评审投入减少约 75%，每月节省约 132 个工程师小时，与这批 PR 相关的事故减少约 30%。

当时脚本和 Agent 独立触发、并行运行，彼此看不到对方的运行结果。团队正在考虑用一个入口审整份 PR，并让 Agent 按需调用第一层检查。值班调查 Agent 则是协助处理每周反馈的一项单独构想。

带回团队复盘时，三种结果可用不同度量。危险变更被误放行要抽样核对生产事件或经验证的近失。可通过的改动被无谓升级要记录交接耗时与原因。应当升级且及时处理的案例则需要看材料是否齐全。比例有意义的前提是有明确定义、确认结果的主体，以及每一类的分母。先建立稳定的采样方式，再把可改的条件落到具体规则。

练习

用这一讲的方法做一次小练习

画出 A 湖表扩宽列后，B 作业向 C 表写入失败的链路，脚本、Agent、运营负责人各查什么？

展开参考答案

脚本查注册字段和已登记依赖，Agent 查仓库代码中的用途和可能窄化的目标列，负责人确认作业在生产仍运行并决定先改下游。

Agent 说“没人用这张表”。怎样改成可审核的审查意见？

展开参考答案

写清查过的仓库、入口和字段，没有在这些地方找到使用。外部查询、临时任务和未登记的消费者仍需用可访问的证据核验。

一条敏感权限变更通过全部检查且 Agent 很有信心，下一步是什么？

展开参考答案

按权限策略交由有授权的人判断。模型应附实际改动、检查结果、风险线索和谁可能受到影响。

如何根据一次错误升级改规则，同时避免把特例扩散？

展开参考答案

记录适用的管道、转换和策略，再增加狭窄判定。用正反样本检查新规则，还应单独观察同类漏判和错误升级。

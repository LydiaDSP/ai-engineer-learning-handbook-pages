学习手册 04 / Stephen Chin · Cassandra Chin

PR 写着“测试通过”，怎样证明它说的是真的？

一份流畅的 PR 描述，可能引用了错误目录、旧版本或失败运行。Stephen 与 Cassandra Chin 展示了如何把改动原因、代码和执行轨迹连接成可核查的证据包。

Tracetoon · PR 证据与知识图约 23 分钟演讲中文导读与讲解 · Lila
PR 证据图与溯源评测成本
导读

“测试通过”到底通过在哪一份代码上？

这场分享从 PR 描述里的一个具体错报切入。模型把会话里出现过的测试命令，写成针对最终改动的成功检查。从代码 diff 可以知道实现发生了哪些变化，跑过什么、测试结果对应哪一版却要查执行记录。

如果交付证据来自两个仓库、几次会话或失败后重试，直接收集更多文本可能让这些事件更难分辨。讲者的图证据包把版本、目录、命令和结果接在一起。这个导读补充了一套实作，先不依赖图工具，手工走一遍从错报到短证据包的过程。

读完可以做什么
  • 用目录、版本和退出状态界定一条测试结论。
  • 为自己的 PR 建一个带未知项的证据包。
  • 用固定样本比较描述质量和完整成本。
导入

代码没问题，PR 的事实仍可能是错的。

Cassandra 介绍 Tracetoon 的出发点：AI 让开发速度加快，但 PR 描述里常有不准确的信息，或者没有把改动解释清楚。两位讲者用漫画人物 Alex、记录证据的 Pip 和负责审查的 Mira，把这个问题串成故事。

审查者真正要问的往往不是“改了哪几行”，而是为什么改、实际跑过什么、结果针对哪一份代码，以及还有哪些情况没验证。

“测试通过”不是一个可以脱离运行记录独立存在的事实。如果描述来自压缩过的会话记忆，或者只根据 diff 推测，工具可能把计划、尝试和真正完成混在一起。

上手

拿一份旧 PR，给每个结论补上证据。

编辑练习：挑一份已完成的小改动，把 PR 里的事实逐条写出来。对每条事实标记“有证据”“证据过期”“没有记录”，不要用更漂亮的措辞掩盖缺口。

  1. 记录被检查的提交或内容版本。
  2. 保留命令、工作目录与执行时间。
  3. 区分通过、失败、未执行、只验证部分路径。
  4. 把说明中的每个验证结论指向对应记录。
请根据代码变更和真实执行记录起草 PR。
每项验证结论必须对应：仓库/目录、命令、被检查的版本、实际结果。
计划运行的检查不能写成已执行；旧版本的成功不能自动用于最终版本。
没有证据的内容写明未验证，记录相互矛盾时保留冲突。
最后用独立的事实核对步骤逐条检查草稿中的主张。

完成标准：另一个人不用相信会话的自我总结，也能找到结论依据。

选只有一两个变化的已完成 PR。在本地或测试环境准备两次检查，一次针对较早版本，一次针对最终提交。另留一条只计划没有执行的命令，测试系统是否会误报。

第 1 步

标记每次检查的对象

不同会话执行的命令有可能同名，而且可能在不同目录。

展开可复制的提示词
列出所有与 PR 有关的命令。记录开始目录、仓库、提交、真实输出和退出状态。没有记录的项标为未知，把命令文本与实际发生区分开。

完成标志　检查绑定到可核验的目录和版本，旧成功可以识别。

第 2 步

提取简明证据包

给写稿 Agent 一组小而可回溯的材料。

展开可复制的提示词
只留当前需求、最终 diff、重要验证、失败或未验证事项。为每条事实附记录 ID。出现重试时保留旧尝试及随后结果。

完成标志　证据包可以支撑说明里的事实，新读者知道去哪查原始记录。

第 3 步

从证据起草，再独立核对

生成一段流畅描述与审查事实是两件工作。

展开可复制的提示词
根据证据包起草短 PR 说明。另一轮把每个完成主张拆出，逐条核对其版本、目录、结果与其它冲突。缺证据就给明确标记。

完成标志　未执行的命令留在未验证项，最终提交没有收到旧版本的通过结果。

第 4 步

给质量和开销都留记录

改过流程后要清楚费用变化对应哪个环节。

展开可复制的提示词
用同一批 PR 比较旧流程和证据包流程。统计错报、应有而未写的限制、模型 token、模型费用与人工审核时间，分别保存。

完成标志　不把模型费用视为总成本，能指出哪一类错误减少。

轨迹

上下文告诉你发生过什么，轨迹才能帮助你核对。

两位讲者指出，常见的 PR 生成方式依赖当前会话日志或 diff。长会话经过压缩后，执行细节可能丢失；diff 又只描述代码变化，不能独自证明程序曾被执行或测试通过。

他们把调查范围扩展到不同会话的轨迹：哪些操作确实发生过，工作目录在哪，命令针对哪个仓库，结果怎样与这次提交关联。

演讲中特别强调 CWD，也就是命令开始前的当前工作目录。一个包含 cd 的命令，可能在后续切换目录；记录时混淆开始位置与目标位置，就可能把另一个仓库的测试算到当前 PR 上。

为什么只保存“测试通过”的一行日志不够？

还需要知道这行来自哪次运行、哪个版本、什么环境。证据越接近执行现场保存，事后重建的空间越小；但日志本身也需要正确归属。

教学推演。假设终端 A 在提交 X 上运行单测成功，终端 B 在提交 Y 上运行类型检查失败；随后改动到 Z，日志里只是计划重跑两项。对 Z 可交付的说明是两项均未验证，并附此前的相关失败。这样能够讨论接下来做哪一步，不会让已过时的绿灯覆盖现在的不确定性。

跨会话比较时应先分出三个时间点。命令打印时的工作目录、实际启动测试时的目标、提交发生后留下的代码状态。假设一次操作日志写着“cd packages/ui && bun test”，只抄开始目录会把 UI 测试归到根目录，只抄命令也不知道它有没有运行到 test。好的证据包允许读者顺着对应该次执行的输出判断阶段，不能相信字符串本身。

操作记录如果来自不同时区或序列号，先把事件归到同一条可追踪的会话。时间接近只是线索。两份日志用同一个版本号、确实属于同一个工作目录，才能支持归属。记录不全时宁可把这次执行挂作待查，也别为了生成漂亮的 PR 文字连上一条未经证实的边。

主张

更多上下文，也可能把错误的结论写得更像真的。

Tracetoon 早期流程会寻找分支相关轨迹、调查、审查描述，再补充上下文继续修改。讲者认为这种方式提高了质量，但仍会留下事实错误，也反复消耗模型调用。

他们展示过一条关于测试的错误主张：轨迹里同时运行了 bun test 与 bunx tsc，在那次项目条件下需要按顺序运行，后续又没有足够的通过记录。PR 却给出了超出证据的成功结论。

这不是“这两个命令在任何项目里都不能并行”的通用规则。演讲的教训是检查真实执行条件与后续记录，而不是从一次案例推出所有项目的限制。

他们尝试降低撰写模型的成本，发现仅换便宜模型并没有解决证据问题。真正需要改变的是事实如何组织、重复调查如何减少，以及审查者拿到了什么。

演讲里 bun test 和 bunx tsc 同时出现，问题与当时的实际运行方式有关。可以用一个教学版反推怎样写 PR：若类型检查需要前一项产生的文件，第一次并发失败应保留。串行重跑也只对那一次的提交有效。交接里给出“失败后在同一提交重跑并通过”与“下一提交还未跑”两个格子，阅读者便能找到下一步要做的工作。

证据图

先把关系整理好，再让模型写。

两位讲者介绍用嵌入式图数据库 Relate 组织证据。图中的关系把“为什么做”“改了哪些代码”“跑了哪些检查”及其来源连接起来，再提取与当前 PR 相关的一份精简证据包。

这样，撰写者不必每一轮都重新翻查所有会话，审查者也能对照同一组有来源的事实。图的价值在于可复用的关联和检索，而不是让任何写进图的数据自动变真。

他们在这个任务中保留较强的撰写模型，使用成本较低的审查模型做事实交叉核对。讲者认为高质量表达与机械核对的要求不同。这是针对其流程的配置经验，仍需用自己的任务集评测，不能当作固定的模型等级规则。

演讲把部分图计算称作相对于模型调用“几乎免费”，实际仍有计算、存储和维护成本。不能把 token 下降直接等同于总成本下降同样比例。

图关系中，命令和输出本身可以被两份证据误连。比如命令开始于仓库根目录，执行串中才 cd 到辅助工具。只存一个路径，审查者不知道从哪算起。把开始位置、实际运行目标、版本和结果并排保留，图才能把同一事件交给写作者与审查人。

精简证据包的边界是先支持当前提问。要证明测试是否跑过，就返回这次 PR 的最后提交、执行事件、输出和可能的冲突记录。要说明改动为何发生，才应补最相关的需求和讨论。所有原始记录仍可回查。一次返回中足量但精简的事实让撰写者少翻旧会话，让排查的人在发现矛盾时还能回到原始位置。

评测

质量分数变高，还要问比较了什么。

演讲用 PR Bench 对照轨迹、代码和模型裁判评估 PR，并提到人工复核。讲者报告的例子包括口头概括的约 74→76、82→86 分，以及 token 用量约减半。原图更精确地给出 Claude 74.2→76.2、Codex 82.4→86.8；另一个成本图给出每份 PR 起草费用下降 38% 和 41%，并明确排除评估裁判与人工时间。

这些数字说明他们观察到改善，不足以证明任意项目接入图后都能得到相同收益。样本量、PR 类型、模型配置、裁判偏好、图构建成本，以及最终人工接受率，都会影响结论。

更有用的复现实验是固定同一批 PR，让原流程与证据包流程分别输出，比较事实错误、遗漏、修改轮次、模型 token、实际费用与耗时。内容质量和成本应该同时看。

一次更有意义的对照

先选一组包含旧测试结果、跨目录命令、失败后重跑的 PR。要求两套流程都回答“最终提交究竟通过了哪些检查”。只比较字数更短或描述更流畅，测不出证据归属是否正确。

编辑设计的实验建议，不是讲者已完成的额外测试

演讲里的 PR Bench 以对照轨迹、代码和模型裁判来评价描述，数据指的是本场流程与样本。口头所说的大致 token 变化，与幻灯片上的每份 PR 起草费用并非同一指标。图表先保留质量分数，复测时也要把图构建、检索、审查和人工改写放入各自的账。

如果自己做 A/B，对照集至少要包含容易骗出流畅主张的样本。有早期成功但是最终版未知的一条，有非目标文件的运行成功一条，有类型检查失败并在同一版本重跑一条。比较成功结论的准确性、报告未知的完整性以及人工修订耗时。把旧流程与新证据包跑在同一批固定 PR 上，模型换代的影响最好另测，避免对不上图里的因果问题。

两组质量分数的增幅可以放在同一个量表理解，费用记录的分母需要单独写清。就算某次写作调用少花了 38% 或 41%，如果索引与人工检查用了很多时间，团队的实际时间预算仍可能不同。复测表可以记录证据提取、文本起草和复核的调用级成本，再另列人工时间，使成本讨论落在具体工序。

练习

让下一份 PR 少一句无依据的“已经”。

修改前测试通过，能写“本次改动已通过测试”吗？

展开参考分析

不能自动这样写。要说明检查对应的版本；如果最终改动没有重跑，应标记未验证或说明已有证据的适用范围。

图里有“检查通过”这个节点，就能直接相信吗？

展开参考分析

要继续追溯它对应的执行记录、目录与提交。图表示关系，不保证输入事实正确。

token 减半，就能宣布总成本减半吗？

展开参考分析

还需要计算图构建、存储、查询、维护、人工审查和失败重试等成本，并保持比较条件一致。

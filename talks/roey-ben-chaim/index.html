审查 Agent Skill 时，怎样看见实际行为？

核对任务覆盖面，把会话轨迹与进程、文件和网络记录连起来，再评估 Skill 是否超出了授权范围。

导入

先弄清这次访问为何发生

Roey Ben Chaim 用一次 Azure 诊断说明误判从哪里来。看到程序读取敏感配置后，可以先核对用户有没有要求诊断，读取范围是否符合任务，用到的信息最后去了哪里。三个问题都能从授权和运行记录中寻找证据。

Skill 作为软件依赖，可能携带说明、资源或脚本。入口的静态检查有用，实际采用前还得核对它所加载的其他依赖和运行时的影响。

覆盖

给测试一项可完成的任务

Zenity 的初版把 Agent、Skill 和任务一起放进隔离环境。遇到应当使用某项服务的测试，空环境容易让任务过早终止。团队于是让环境准备组件按测试场景补足服务和项目状态。

先列清楚要覆盖哪些工作。一项涉及部署的 Skill，设置、发布和恢复三种任务会留下不同的行为记录。逐项标记哪些路径已观察、哪些被阻止、哪些还没走到，复核者就知道现有结论适用的范围。

证据

从工具调用追到实际影响

完整录像在 06:03 转入工具轨迹及其证据缺口。一次调用可能触发子进程，而子进程读写文件、发起连接的记录散落在不同层。把它们用同一次运行的编号、时间和进程关系连起来，才能回答是谁做了什么。

判定时可以分别记下事件、依据和下一步。例如“出现一个无法归属的出站事件”是线索。复查发起进程、任务授权和目的地，才能决定应怎样处置。

发现

怎么读研究团队报告的数字

团队报告，在检查数千个 Skill 后识别了 100 个恶意条目。演讲缺少可用来计算总体比例的精确分母，也没有说明漏检情况。把它记为这轮调查发现的数量即可。

另一宗仿冒项目调查里，讲者提到相关条目累计约 170 万次下载。一次下载和一次执行是不同事件。要估计受影响范围，还得核对安装、运行和数据访问记录。

采用

把 Skill 纳入依赖审查

记录 Skill 的来源、批准的版本和运行所需权限。用隔离环境观察与任务相关的文件、进程和网络事件。版本或外部依赖变化时，用之前的测试重新检查，必要时增加相应的覆盖用例。

演讲最后把这个原则扩展到网页、数据库记录和包。它们都可能给 Agent 带来新的材料。系统要能回查这份材料从哪里来，以及它何时影响了运行。

上手

只用模拟日志给三次运行做分类

场景是一项报告导出任务，许可范围只有读取模拟报告和写入本地导出目录。以下记录为教学示例，使用纸笔或表格即可完成练习。

  1. 运行 A 成功读取 fixture/data.csv，生成 out/report.json，再用本地校验器核对字段。
  2. 运行 B 也生成报告，但同一运行号下的一个后续进程出现了未授权的出站事件。日志没有记录内容。
  3. 运行 C 启动后因模拟数据服务缺失而停止，尚未到达导出步骤。

给三次运行分别填写“已观察事件、授权依据、尚缺证据、处置”四栏。完成条件是能指出哪次通过已测路径，哪次应该停止自动批准并复核，哪次需要补足环境再测试。

练习

用三道问题复核判断

运行 A 可以批准到什么范围？

这次模拟导出路径符合预期。换任务、换版本或换依赖时，应根据变化补测。

运行 B 缺少哪些证据？

先确认这个进程由哪个调用启动、出站目的地是否在许可范围以及日志能否查到所传数据。保留已有记录并转人工复核。

运行 C 应该怎样记录？

标为环境未准备好且导出路径未覆盖。补上模拟服务后重跑，仍保留第一次停止的记录。

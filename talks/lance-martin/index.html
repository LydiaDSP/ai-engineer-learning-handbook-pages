Claude 怎样组织千名 Agent，又怎样修正自己的记忆？

一场关于费马大定理形式化的协作实验，三类关于记忆的观察。Lance Martin 从 Lean、Git 和数据库讲到任务结束后复查笔记与重建 Wiki 的 Dreaming。

导读

换一班 Agent，项目还知道自己做到哪了吗

Lance Martin 展示的两项实验都从「下一个执行者要怎样接着做」说起。费马大定理的 Lean 形式化需要让大量工作者知道哪一条子命题有人在验证、哪一个结果已经合并。Pokémon 的下一次会话只有一堆留下的笔记，恰好一条写错位置的记录会让它又掉进旧陷阱。两处问题不一样，前者要共享正在变化的事实，后者要把过去写下的事实重新核对。

演讲给出了两个很具体的工程边界。并行实验省去了专门为证明设计的编排工具，仍提供 Git、数据库、隔离和监控。记忆实验把信息整理放到任务之外，仍保留原来可以检索的会话记录。你可以从一份多人维护的文档练起：先建立可核验的共享记录，再让后来者通过它还原一个决定，把不可靠的记录找出来。

读完可以做什么
  • 看懂千 Agent 实验保留了哪些基础设施
  • 设计包含任务进度、依赖和验收的共享表
  • 用同一批问题比较原文检索、原始笔记和整理稿
上手

用三名 Agent 试一次接力

教学案例：整理项目的安装文档，分别处理 Linux、macOS、Windows。原文里存在一条旧命令，新的安装入口已经写进当前仓库。输入是固定提交和一份带时间的旧会话记录。最后交付三段能复查的文档和一行保留旧记录的勘误。

第 1 步

写出可单独检查的小工作

先划分交付边界和依赖，减少多人编辑同一段产生误解。

展开可复制的提示词
基于提交 SHA 列出安装文档的子任务。每项输出 ID、平台、要查的文件、输入依赖、完成证据和责任人。指出哪些内容是三平台共用的，哪些必须单独验证。把安装失败的处理放成单一共享任务。

完成标志　工作表有唯一 ID，能回答共用说明由谁改、平台项怎么确认。每个认领对应明确修改范围，解析不清的依赖进入待判断。

第 2 步

让共享记录能支撑合并

协作表只表达谁在做什么；工具通过才表示完成。

展开可复制的提示词
用状态待认领、处理中、待验证、已通过记录各平台。把结果写到自己的分支，并在任务表填上可追溯提交和验证命令。合并前由独立检查核对锚点和命令；缺执行环境就标注未验证。

完成标志　用一次模拟冲突核对状态，确保只有一个人能认领共用条目。待验证不能自动写成已通过。测试结果能找到提交和命令。

第 3 步

重看旧经验，把错误留下可追溯的勘误

过时命令被写进摘要后，下一次会话仍可能信它。需要查当前源码和记录版本。

展开可复制的提示词
读取带时间的旧会话与当前仓库。检查旧命令是否还存在并找出它的生效条件。保留原始日志，新增一行状态和依据，说明旧命令过时或仅适用旧版本。没有证据时给出待核对项。

完成标志　示例输出带有状态、源文件、提交范围和记录日期。旧记录仍可回查，当前手册不会继续把过时命令当默认。

第 4 步

开新会话重回答

整理过程会消耗时间，后续得查到有用的知识才值得做。

展开可复制的提示词
新会话回答同一批安装问题。分别只给原文检索、原文加旧笔记、原文加校过的 Wiki。输出答案、来源版本、是否沿用旧命令与总耗时。先约定哪些问题必须拒答。

完成标志　同一套判定表能比较三种输入。若 Wiki 提高了速度却误导平台选择，保留错答与来源。发现资料缺失时，能指出后续要补哪项证据。

第 1 节

把已有证明变成 Lean 可以检查的对象

费马大定理早有数学证明。对这场实验来说，工作在于把证明写成 Lean 能检查的形式。这个任务横跨许多相互依赖的中间结论，也给 Agent 提供了清楚的验证目标。

回看这一节 · 03:48:37 ↗

报导里的「形式化」有一个容易被读成别的意思的地方。Wiles 的人类数学证明已经存在。这里的成果是在 Lean 中表达并连接足够的引理，使检查器能判断导出的结论是否符合所采用的定义与前提。把这个例子移到工程里，比较接近将已定的规则细写成一套机器可以检查的约束，迁移之前仍需要人确认规则定义。

早期约十几名 Agent 借助 Prove2Me 跟踪证明状态和依赖，仍需要人工协助。后来的实验扩大一组工作者，同时撤去这套数学专用协调工具。规模、模型版本和编排条件都不同，这段材料足以讲两次运行怎样组织，不能单独估算“少一层工具”造成多少提升。

第 2 节

给千人队伍共享状态和明确边界

一条证明是否成立由 Lean 检查。领队如何分工、组员怎样同步进度，则交给 Git 和 SQL 上的协作协议。把这两件事分开，才看得出实验究竟减少了哪一层的人为设计。

回看这一节 · 03:50:54 ↗

共享数据库让工作者能查询其他人的进展。单个沙箱的文件不必对全队公开，代码结果用 Git 提交交流，任务和公告在数据库交流。自己能看到任务表是一回事，能否把另一个工作者的文件改坏是另一回事。给普通项目设计类似分工时，建议先列出最少共享面，再为认领、共享资源与合并分别定权限。

Anthropic 还监控工具调用，定时复盘记录。演讲提到网络受到限制。把一千个 Agent 集合到一个任务，并不意味着给它们同一把钥匙。课外练习可以在测试仓库开始，按工作所需分配读取、分支写入和合并，留下足够的复查线索。

第 3 节

领队怎样分工，进度怎样被看见

这几分钟适合跟着图一起看。公告和分工表能告诉组员现在往哪条路走，提交状态则让别的 Agent 看见哪些前置工作已落地。遇到较难的引理，团队又把它拆成一棵新的任务树。

回看这一节 · 03:52:42 ↗

那张读写时间图能帮助判断系统何时开始组队。领队先建公告、角色、共享笔记、子任务和落地状态，后续工作者通过表跟进。公告频次只能说明有人在沟通；想看到证明接近完成，要查子任务合并后的依赖是否都满足，末尾 Lean 检查状态怎样。

Martin 描述约 30 小时、约 60 个中间命题的推进。较难分支需要继续拆出相互依赖的小工作。在自己的项目里，先留出从“暂时没人能做”切到“依赖已满足”的条件，比只留待办和已完成两个状态更有用。为了防止任务树越拆越大，可以约定每条子任务都附一个可以独立核验的输出。

第 4 节

会话里的笔记怎样成为以后用得上的记忆

一段调查刚结束时，Agent 看到的是手头问题。后来的会话需要的是保留下来的高价值事实和线索。Martin 先用数据库问答和游戏说明，模型会不会挑、会不会读，都会影响同一个记忆目录的价值。

回看这一节 · 03:55:42 ↗

CL-Bench 数据库问答序列让模型在 40 道题之间重开会话，只有文件夹保留。这种安排能问一个很现实的问题：经过上次尝试后，模型会不会自己记下一条后来仍然有用的事实？Martin 观察到更强模型更会在适当时机读写；收益随模型变化，因此只把空目录挂上去，还需要检查使用行为。

演讲中 Pokémon 两幅目录图可以从“下次找东西”来读。流水账记录了当时视野里的一切，空间大却降低了单位阅读的价值。紧凑战术笔记保留普通画面里难以重新拿到的状态与规律。图块大小反映文件量，游戏进度是在另一条轴上观察；文件数不能直接代替策略效果。

第 5 节

Dreaming 怎样从记录里重组知识

原始会话、当场笔记、Wiki 和预先载入的上下文分别解决不同的查找问题。Dreaming 给系统一个事后检查的机会，把线索放到将来最容易用到的地方。

回看这一节 · 04:00:51 ↗

可以把一条旧经验分成三份来维护。原始转录保留当时到底做了什么；笔记写下可能有用的观察；整理稿才把多条来源连成一条可以导航的知识。三份材料该在不同时间进入会话。如果每份原始记录都自动进新会话，阅读成本会很高；若只让 Agent 看摘要，一条已经过时的经验就很难核对。

持续整理不是让模型自己把旧内容永久覆盖。教学例中，旧安装命令可以保留并标注适用版本，再把当前有效命令带着证据放到 Wiki。对某条记忆找不到原始证据时，可以标成待核对。日后整理回答变快的同时，读者仍能打开原文确认原因。

第 6 节

一个错误地点怎样让 Agent 反复走错

游戏例子让错误的后果容易观察。Agent 写下了一个错误地标，之后经过那里时仍采用旧记录。可以顺着曲线看，在有无事后检查的两种条件下，错误怎样影响后续关卡。

回看这一节 · 04:02:21 ↗

位置笔记一开始很合理，因为同一场景会反复出现。演讲展示的是，笔记错误被保留下来后，下一次会话还会把它当真，于是反复掉进同一处机关。对读者来说，可以把这条曲线拆成两个时刻：第一个是错误写入，第二个是错误被重复使用。只提高记录数量会让后一个问题更难看出。

故障发生后，先把失败动作和当时读到的记忆一并留下。重看任务记录时，查这条记忆的来源，确认它该被改写、缩小适用范围，还是标成需要人的判断。改过后用同一条路径重跑。游戏进度曲线覆盖了回退和继续推进，讲者用来说明这次整理在该情境里的表现。

第 7 节

Wiki 与检索可以一起用

最后的公司语料案例把话题拉回日常工作。Wiki 让人和 Agent 看见概念之间的关系，原始检索帮助查证具体细节。小型评测能比较各自作用，也能发现条目背后其实没有页面。

回看这一节 · 04:03:52 ↗

演讲最后把语义检索和 Wiki 放进同一项问答任务比较。原文检索能拉出与问题相近的材料，整理稿则能把跨多份资料的关系提前组织好。若 Wiki 中的页面只有占位链接，问答仍需要读原文；反过来，只有原文检索时，解释分散在多份资料中的同一条约定也可能很慢。

Anthropic 用脱敏资料和 25 道题测试这三种信息条件。只查原始资料的基线约 53%。投入更多整理计算时，Wiki 帮助回答更多问题。两者并用的成绩高于单独检索原始资料。用到自己的项目时，先选几道确实依赖内部文档的真实问题，记录答题正确性、证据可追溯性和整理成本，再判断哪一类资料最适合做成 Wiki。

练习

用这一讲的方法做一次小练习

实作一。给三个协同维护文档的 Agent 设计一轮带验收的交付。写出它们共享什么、怎样防止重复认领、谁决定交付合格。

展开参考答案

共享能记录归属、依赖和完成状态的任务表，以及带审查分支的 Git 仓库。领队发公告并分派任务，工作者登记认领与证据。由独立的链接检查、断言和人工抽查确认交付。可以先用三项小任务验证协议能否处理分工和合并。

实作二。选一个会反复查询的项目问题，做三组记忆对照。保留一条互相矛盾的历史笔记作为检查项。

展开参考答案

用同题分别测仅检索会话、会话加未整理笔记、会话加整理后的 Wiki 与原文检索。记录答案、证据链接、是否重复旧错误和总耗时。整理时保留出处，把互相冲突的记录交给证据核对再决定。

理解检查。Lean、Git 和 SQL 在千人实验里分别有什么作用？

展开参考答案

Lean 检查证明步骤。Git 记录代码和提交。SQL 让 Agent 交换分工与进度。这几个角色支持了不同层次的验证和协作。

理解检查。CL-Bench 的条件怎样测出记忆读写能力的差异？

展开参考答案

每题重启会话，仍保留同一个笔记目录，并只告诉模型它可用。在这些条件下，不同模型需要自主判断何时写入和检索，结果因此可以对照。

理解检查。为什么 Wiki 里的占位链接和 Pokémon 的错误位置是两类问题？

展开参考答案

占位链接表示所需内容还没被写出来，适合找证据补全并更新索引。错误位置已有明确记录却引出错误行为，需要追溯原始证据并纠正。

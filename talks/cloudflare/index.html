Cloudflare 如何让小模型分担 Agent 的判断和提取？

从 Cloudflare 的自训模型说起，用一次失败的 CI 排查看 Clef、Clairic 和通用大模型怎样配合。

Cloudflare · Group Product Manager约 20 分钟演讲中文导读与讲解 · Lila
决策模型结构化提取CI 排查
导读

失败的 CI 需要哪些判断？

收到一条“帮我看看 PR 为什么没通过”的消息后，排查流程要读出 PR 编号，选择适用的工具，再用日志说明失败原因。这些环节的输出各有不同。编号有固定类型，工具来自事先给定的清单，最后的原因需要把证据串起来。

Michelle Chen 从 Cloudflare 的基础设施讲到 Clef 和 Clairic。她用一个 CI 演示说明，怎样让小模型分担工具选择和字段提取，把综合判断交给通用大模型。读到演示时，可以沿着每个节点核对输入、输出和证据。

背景

Cloudflare 为什么自己训练模型？

Cloudflare 最早用遍布各地的基础设施做内容分发，后来在同一个网络上增加 Workers 等计算能力以及 KV、R2 和 D1 等存储能力。开发者可以用这些组件写应用、保存状态和运行 Agent。Workers AI 又增加了模型推理服务。

Cloudflare 一开始押注小模型，并在边缘网络布置 GPU。讲者回顾，前沿模型后来走向更大，Cloudflare 也开始托管大型模型。Jev 所代表的决策模型给小模型带来了另一种用途。有限选项的判断有机会用小模型快速完成，靠近用户的推理节点也就更有意义。讲者把这两条路线都纳入 Agent Cloud。

模型分工

先提取材料，再选择可执行的步骤

Clairic 负责提取。输入可以是工单、聊天消息或日志。提前写好要提取的字段，例如 PR 编号、错误类别和证据所在行。下游可以用字段类型和原文行号检查提取结果。

Clef 负责选择。把候选工具或路径交给它，从中选出与当前任务相关的项。业务代码再校验候选和参数，调用允许的接口。需要解释多条证据、形成诊断结论时，由通用大模型综合判断。

Clairic 和 Clef 的顺序取决于输入。对消息先提取字段再选路径也可以。在演讲的 CI 流程里，先缩减工具清单，再提取 PR 编号，并在工具返回后第二次提取日志证据。

CI 排查

把筛工具、读日志和解释放到各自的节点

  1. Clef Flash 从约 40 个候选工具中筛出可能有用的工具。讲者以保留 10 个为例。
  2. Clairic 从请求中取出 PR 编号，编排代码校验参数并调用所需接口。
  3. 再次调用 Clairic，从日志中提取报错和相关行。可保留原文引用，让最终结论能回到日志核实。
  4. 大模型阅读结构化证据，给出初步结论和建议。若字段缺失或日志里有 相互冲突的证据，可保留疑问并复核原始日志。

如果提取时把后续报错或不符合预期的证据丢了，最后一句诊断写得再清楚也没法补回信息。评估时应检查证据保留情况，再看综合答案和成本。

演示对照

分开记录现场运行和此前一次运行

现场演示中，两条路径对同一案例给出了相同答案。幻灯片显示耗时从 25.4 秒降到 8.1 秒，费用从 0.0230 美元降到 0.0064 美元，大模型调用由 6 次降到 1 次，大模型 token 从 39,374 降到 1,883。口述将 token 约为 4 万和 1,800。此前一次运行中，全用大模型约 17.2 秒，混合方案约 9.2 秒，成本低约 72%，大模型调用由 5 次降到 1 次，token 少约 94%。

这是两个演示条件下的观测。若要决定是否上线，可以准备多种失败日志和缺字段的样本，对比诊断准确率、证据覆盖率、端到端耗时，以及包含提取和决策模型在内的总成本。

上手

用三条假日志做一次排查对照

准备一个本地文档作为模拟查询结果。目标是输出 pr_number、failed_step、evidence 和 next_action。固定 next_action 的候选为“查类型错误”“排查依赖超时”“补充信息”。

A  帮我看一下 PR #842。测试为什么没过？
日志 21  npm ci completed
日志 55  typecheck: src/report.ts:18 TS2322
日志 58  test was skipped
B  帮我看 PR #843。
日志 14  npm ci: network timeout while fetching dependency
日志 16  build was skipped
C  昨晚的 PR 挂了，帮我看看。
没有编号，也没有日志。
  1. 让同一个通用模型一次读完整输入，产出四个字段并保留日志行号，记录调用次数和耗时。
  2. 用作业分工重跑。先单独提取编号和证据，再从固定选项选择动作，最后生成一条简短说明。用不同提示词模拟专用节点也可以。
  3. 把两轮结果对照参考答案。检查所选动作是否合理、结论能否回到原始证据。若服务提供 token 或计费数据，把每一步都计入比较。
展开参考结果

A 为 PR 842，失败步骤为 typecheck，证据是第 55 行。下一步查类型错误，第 58 行只说明测试被跳过。B 为 PR 843，失败步骤为 npm ci，证据是第 14 行。下一步排查依赖超时。C 保留空编号和空证据，下一步请求提供 PR 编号或日志。

完成后应能指出两种做法在至少一个样例上的差异，并解释把哪些原始证据保留到最后一轮。

复盘

检查三处容易省错的开销

候选工具缩减后，关联证据为什么可能变少？

展开参考分析

筛选器可能漏掉某个必要工具。可用标注案例核对必需工具是否还在候选里，并为缺证据或工具结果冲突的情况安排回退。

模型给出 JSON，原始日志还需要留吗？

展开参考分析

需要保留可追溯的原始证据。JSON 方便传递字段，日志行号和原文片段可用于抽查，也能辅助处理提取失败。

现场减少了大模型调用，怎样验证整个流程确实更划算？

展开参考分析

用同一批样本和同一验收规则比较。统计所有模型的调用成本、端到端耗时、超时或回退比例，同时复核失败诊断的质量。

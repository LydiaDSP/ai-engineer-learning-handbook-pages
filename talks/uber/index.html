两条绿灯 PR，为什么会让主干变红？

从 Uber 的 Go 单体仓库开始，了解合并队列怎样在吞吐和主干可靠性之间调整验证方式。

Uber 开发者平台约 28 分钟演讲中文导读与讲解 · Lila
合并队列CI主干可靠性
导读

CI 上的两盏绿灯，回答的是哪两个问题？

假设主干在 X。PR A 和 PR B 分别从 X 出发，各自的 CI 全绿。A 先落地之后，轮到 B 的时候，主干已经到了 X+A。B 的旧绿灯只检查了 X+B。要知道真正会进入主干的版本是否可用，得验证 X+A+B 或接受一次组合失败的可能。

Uber 的 Preetam Dwivedi 和 Manjari Akella 从这个例子进入 Go 单体仓库。请求变多以后，一味多做组合验证会挤满机器，一味放行又会把失败转嫁给下游开发者。团队先改准入，再让系统代管延后的工作，然后针对弱冲突减少部分组合检查。最后，他们让已经过验证的主干状态有一个可以独立追踪的入口。

读这场时可以把三份证据放在手边。一份是某个候选合并状态的构建结果，一份是已经落地主干的后验测试，还有一份是下游实际消费的提交。有了这三个对象，吞吐、等待和恢复就能分别讨论。

读完可以做什么
  • 画出单 PR 验证、候选组合验证和合并后验证各在测什么。
  • 用受影响目标估算哪里值得并行，再解释放宽冲突的代价。
  • 写出一份能检查的双指针演练，把稳定消费者和处理故障的值班者分开。
上手

四步演练一次两条 PR 相互影响的合并

选一个练习仓库和两条改同一行为的变更。下面以金额校验接口为教学例，仓库名和结果都可以替换。可以先在纸上演算，再到临时分支验证。保存每次测试所用的提交标识、命令和结果。

第 1 步

先让两条独立绿灯和一条组合红灯同时出现

以 X 为共同基线。A 更新校验方法与自己的调用点。B 增加一个仍使用旧接口的调用点。为便于展示，先确保 A 和 B 各自都通过现有检查，再观察 A 合入后 B 的组合结果。

展开可复制的提示词
请只分析我给出的练习仓库，不提交或推送。基线为〔X 的提交〕，两项改动为〔A〕和〔B〕。分别列出 X+A、X+B 与 X+A+B 的预期检查，以及每项检查能证明什么。指出哪条断言能捕获 B 引入的旧接口调用，并给出最小证据记录格式。

完成标志　能从测试记录看出每条绿灯对应哪一份代码。切换到 X+A+B 后，原本通过的 B 检查出现预期失败。

第 2 步

把候选构建的数量写出来

把可能落地的顺序、共享构建目标和资源估算写成表。想要并行做更多活，先明确哪些路径可以共用一次构建，哪些需要保留组合检查。此处把替代规则放在纸面比较。

展开可复制的提示词
根据〔请求列表、构建目标和每次构建耗时〕设计两套候选验证安排。一套按顺序验证组合，一套让无共享目标的分组并行。请每行列出要测的状态、它依赖哪些测试以及取消时会丢掉哪份证据。不要把影响范围的分数当作事故概率。

完成标志　每个候选状态都有可读的提交组合和依赖说明。对增加的并行，你能指出哪一次构建省下了，哪一类组合证据随之减少。

第 3 步

为落地主干和已验证版本各留一个指针

在演练记录中让 X+A+B 落地后失败。保持原来的已验证指针，等修复 C 的组合状态通过后再推进。即便你没部署真实的合并队列，也可以用单表模拟这个过程。

展开可复制的提示词
请模拟三轮。第一轮 X 的检查通过，第二轮 X+A+B 落地但检查失败，第三轮 C 修复后整体检查通过。输出每轮 main、verified/main、检查证据、下游该用的提交和需要谁接手。失败的轮次附一条处理工单草稿。

完成标志　失败轮次中，主干位置可以前进，可信指针保持上一个通过状态。恢复轮次要能找到触发推进的检查和实际使用的提交。

第 4 步

让队列变快的账和故障的账一起记

从一次演练可得到具体的等待、验证覆盖和恢复记录。上线前，把峰值吞吐、长尾等待、可信指针滞后以及值班恢复耗时放在同一张观察表里，避免只对着单个高峰数字下结论。

展开可复制的提示词
帮我为〔试点仓库〕写一页验收记录。每项指标注明分母、采样时间、按大小分组的方法和证据来源。请同时记录普通与高峰时段、放宽了哪些组合，以及发现故障后何时告警、修复和确认恢复。

完成标志　读者可以复算至少一个指标，并找到负责人的具体动作。表里能看出吞吐有无提高，以及尾部等待或已验证版本滞后有没有一起变差。

第 1 节

两条绿灯 PR 怎样让主干变红

提交队列真正要验证的是某个合并后的代码状态。讲者从两条独立通过的 PR 开始，接着把问题放回 Uber 的 Go 单体仓库。这个顺序很重要，先弄清系统承诺了什么，才能理解后来为何改变承诺。

回看这一节 · 00:00:00 ↗

逐个检查的绿灯会被误读，因为 CI 界面通常把结果贴在 PR 上。更耐看的记录方式是把结果贴在提交组合上。一个绿灯表示某个明确状态跑了一组指定命令，可以被重新执行。以后遇到 rebase 或先后顺序变化，工程师能够回来问这条证据是否仍然覆盖即将落地的代码。

演讲没有承诺把任何两个变更都两两组合去跑。SubmitQueue 提前验证最可能落地的候选，并用依赖和目标信息识别确实能独立推进的工作。这里的关键动作包括选择要预测的顺序、尽早利用已有结果、保证最终落地能找回对应检查。

第 2 节

并行验证做了什么，哪里先堵住

排队成本来自要同时验证多少候选状态。缩小受影响范围、挑最可能落地的组合、让小变更先走，分别作用于不同的等待来源。

第 3 节

先保护队列，再接管开发者的等待

Uber 的第一版把高峰期的资源留给大量小变更。讲者把两件事分开看，一是队列吞吐有没有变好，二是被延后的开发者今天还要不要守着系统重试。

回看这一节 · 00:08:03 ↗

高峰期拒绝大变更给其他人腾出了算力，但成本集中压在少数人身上。共享库负责人不得不重新排自己的日程，记着过几个小时回来试。有了延后队列，系统会保存未进入主队列的请求，等有容量再放进去。它仍然需要监控大变更等待了多久。

实际读数字时，可以同时问这一小时有多少请求抵达，以及真正落地了多少。团队报告的每小时落地量来自具体阶段或峰值。把到达速率、落地速率和一条 PR 从提交到落地的等待时间写成同一列，会把不同指标混在一起。

第 4 节

放宽弱冲突，换回并行能力

难点在于传递性。哪怕队首和队尾互不碰面，中间的一连串共享目标也可以让它们进入同一组。放宽边需要同时追踪并行收益和组合验证的减少。

回看这一节 · 00:12:25 ↗

六条变更的例子里，A 和 F 不一定共享目标，中间的桥却能让六条请求进入一组。这个情形很容易被只看单条 PR 的大小忽略。工程师可以先画共享目标图，把最小的验证单位和曾经失败的组合贴回去，再讨论哪些边必须保留。

演讲还给了一个容易跳过的选择。全局重算可能让预先启动的构建变得无用。让新到请求选择与当前队列的关系，可以复用部分正在跑的计算。策略的收益取决于还在排的请求和构建命中率，最终要看真实负载。

第 5 节

让经过验证的提交有一个独立入口

main 和 verified/main 指向同一条提交历史上的两个位置。一个反映合并已前进到哪里，另一个记录哪一份整体状态已经通过后置检查。

回看这一节 · 00:19:07 ↗

当主干 D 失败，稳定消费者可以继续用 A。同一时间，值班者从 D 回查失败输出和 A 到 D 的变更范围，再决定修复还是回退。两个人面向的都是同一条提交历史，只是选择它的不同位置。若失败告警只有一个红色状态，没有关联提交和负责人，可信指针也不能自行缩短恢复时间。

复原也走同一个系统。验证失败后，值班者发起修复或回退，经评审和 SubmitQueue 合并，再由 Stovepipe 检查实际落地状态。

用四轮教学例说明这件事。A 单独通过时两个指针在 A。B、C、D 连着进入，D 整体检查失败，可信指针停在 A。若 E 合入后尚未跑完，依赖方继续消费 A。后续 F 和 G 落地后，整体 G 得到新检查结果，可信指针可以推进到 G。B 至 F 每个中间点是否独立通过，仍要看各自的证据。

用这一讲的方法做一次小练习

在纸上画出 A 和 B 的合并顺序。两条 PR 都在 X 上通过，假设 A 修改了一个接口，B 继续使用旧契约。你会增跑哪一个状态的测试？

展开参考答案

先验证 X+A+B 的候选状态。如果顺序可能交换，还要检查真实落地顺序。把验证结果绑定到候选提交和基线，方便事后检查究竟测过哪组源码。

给一组大小不同的 PR 设计准入策略。如何让共享库维护者少做重复操作，同时看见政策对他们的影响？

展开参考答案

先按受影响目标估算验证成本，保留低峰或空闲容量供大变更。持久化延后请求并显示其状态。对大、小变更分别统计 p95 合并时间，再看整体吞吐。

一个连通分量的弱边得分为 0.05。你能据此说组合失败概率为 5% 吗？

展开参考答案

不能。Jaccard 等信号用于排序要放宽的边。若要估计失败风险，需要单独用历史验证数据校准，并持续检查放宽后的实际失败和回退。

main 已到 D，verified/main 还在 A。依赖仓库和负责止损的值班者分别该看哪个位置？

展开参考答案

需要稳定依赖的一方先消费 A。值班者查看 D 的失败证据，定位 A 到 D 的改动。修复或回退合并并通过后置验证后，可信指针再前进。

为上线试点定三项能让你看见副作用的指标。

展开参考答案

记录 p95 合并等待、main 与 verified/main 的时差，以及失败到恢复的耗时。若同时报告吞吐，要把高峰窗口和通常窗口分开，以免一个峰值掩盖尾部等待。

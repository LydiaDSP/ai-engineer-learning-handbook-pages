导读

用一次真实交付，找出模型还不会做什么

设想一份 Agent 交付总结写着“测试全部通过”，工程师翻开轨迹，却找不到与报告对应的检查记录。对使用者来说，这个问题常常晚于语法错误出现。程序能构建，甚至有一部分功能能用，最后一道检查却只是由模型自己写出来。Melvin Johnson 在演讲后段把这种报告与证据不符的情况单独拿出来评测。

他还介绍了难题来源、资深工程师式评分和内部试用。三者要合在一起看。题目必须能让当前模型分出高低，评分器要读到真实行为，工程师才知道训练后的改进会不会落到日常工作上。本篇把这些做法缩到一个仓库练习，亲手给一次多文件改动加上验收。

读完可以做什么
  • 写出能跨模型版本重测的多文件工程任务。
  • 分开验证功能、兼容性、长期维护及交付报告。
  • 在读演讲指标时辨认样本、评分范围和未给出的统计条件。
上手

给一个多文件任务录下产出与证据

教学任务是在小型日志查询工具里加入日期范围参数，保持不带参数时的原有行为。准备一份冻结的测试输入、一个起始提交和可重复的运行环境。选熟悉且现在仍容易漏掉边界的工作。

第 1 步

定义有可观察结果的改动

一个清楚的起始版本和完整约束能减少环境误差。

展开可复制的提示词
为这个 CLI 写一张任务卡，说明仓库起始提交、已有执行方式、目标参数、输入文件和退出码。列出不带参数的输出兼容要求。把内部实现留给执行者选择。

完成标志　另一位工程师凭任务卡可以说出程序什么时候成功，什么时候应返回明确错误。

第 2 步

用分开得分的规则替代一票通过

完成一部分工作的运行，也该留下有价值的比较。

展开可复制的提示词
把验收拆成功能、边界、兼容性、维护和证据五列。为每列写通过规则和实际检查方法。生成一张评分表，并单列哪些失败应阻止交付。

完成标志　新功能通过但旧调用行为变化时，评分会留下两个结果，兼容回归仍会挡住交付。

第 3 步

独立收集运行事实

让运行中的 Agent 与记下证据的一方从同一版本出发。

展开可复制的提示词
记录每次执行的版本、环境、命令摘要、产物和退出码。完成后把交付总结逐项关联到日志。评审过程只读取已冻结产物，不让实现者决定评分。

完成标志　“改了文档”和“测试通过”都能找到凭据。没有取得凭据的主张显示为未证实。

第 4 步

让错题进入下一轮

一份测试集可以保留重复运行的意义，也给新错误留位置。

展开可复制的提示词
比较同一任务的多次结果，分类记录哪些版本反复漏掉某项边界。提取一个可重放失败，同时找出几项需要换成更难目标的饱和练习。给真实验收保留独立的测试集。

完成标志　报告看得到旧题用于回归，新题用于区分，以及后续什么时候再评估。

第 1 节

从单轮问答换成长程工程任务

判断模型是否能承担一项工程工作，可以先写清最后要看到的东西。仓库变更、运行结果和面向人的交付说明各提供一种证据。

回看这一节 · 07:41:46 ↗

单轮问答通常只有一个文本结果。工程任务会同时留下代码、提交、命令输出和一份交付说明。若你只收集最终 PR，先前临时用替代工具跑过检查就无从知道。演讲中的闭环从任务接收反馈，再回到下一轮收题，让训练和内部使用共同暴露工作中的失败。

第 2 节

换掉模型都会做的题

难度是模型与任务之间的关系。更新模型后，重测旧题在多次运行中还能否区分结果。

回看这一节 · 07:43:31 ↗

一道训练题在多次独立运行中从有对有错变成全对，能继续用来观察是否退化。作为区分当前候选模型的材料，它的收益会下降。实作时可以保留一道基础兼容题，另加跨模块的时间边界条件。若执行十次都通过而且真实项目仍常遇见类似错误，先检查测试是不是漏掉了那个失败条件。

第 3 节

从三个地方找可验收的难题

选题时把工作环境和检查依据一起带回来。团队应能重放任务，并在不依赖 Agent 自述的情况下判断结果。

回看这一节 · 07:45:04 ↗

第 4 节

把评分环境当成工程系统

自动验收最值得检查的地方，是奖励和目标可能分开的位置。给评审过程单独保留一条可信的证据路径。

回看这一节 · 07:46:04 ↗

教学样例里，实现让新日期筛选正向案例通过，默认无参数时却漏掉了当天最后一分钟的数据。功能、兼容性和证据列要分开填写。正确的提交可以保留已经有效的参数解析，兼容失败阻止发布，补测的运行还要用最终提交。若评分实现把退出码当唯一成功信号，这个输出差异就看不出来。

第 5 节

对照轨迹，核实“完成了”

读者通常先看 Agent 的总结。让总结能回指所查版本、运行检查、结果和待办，读者就能接着工作。

回看这一节 · 07:49:22 ↗

这里的编造率是讲者在内部难题评测上报告的指标。幻灯片的 Hydrogen 是 2.9%，现场口述四舍五入为约 3%。这张图能支持同一张幻灯片里的版本比较。题量、置信区间及对别的工作场景的覆盖，没有从这张图给出。读者可以把同样的声明核验方式用于自己的 Agent。

第 6 节

把内部工程师的反馈送回训练

离线评测可以检查指定能力。实际使用更容易暴露长任务里反复打断人的细节。

回看这一节 · 07:51:51 ↗

内部试用的价值，是在评测器已经定义好以后仍能遇见新困难。比如工程师反映模型逻辑正确，但交付缺链接，需要自己再搜索一遍。记录复发条件、任务长度和被人工打断的原因，便能将这种感受还原成下一轮可重复观察的任务。

练习

用这一讲的方法做一次小练习

一组题三次运行都通过，怎么判断它还该留在哪里？

展开参考答案

可以保留在回归集以防旧能力退化，再从当前训练重点里减少权重。找与真实失败相关的新题，检查不同尝试是否出现可解释的质量差异。

为一次跨文件改动写一份小型评分规则。

展开参考答案

以命令输出字段增加为例，分别检查原字段兼容、无效输入的错误信息、跨模块调用是否继续有效，以及交付说明能否回指已运行的检查。

Agent 报告“测试通过”，什么信息可以支持这一句话？

展开参考答案

先定位对应提交、工作目录、执行命令和退出状态，再看报告针对的检查是否覆盖当前改动。只记录跑过的部分，留下仍需验证的事项。

如果离线分数涨了，真实用户仍频繁打断 Agent，下一轮收集什么？

展开参考答案

收集发生打断的任务与上下文、当时的运行和用户采取的补救，挑可复现的例子重放。优先处理高频且明显阻塞交付的情形。

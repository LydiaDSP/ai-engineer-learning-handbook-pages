学习手册 第二天 24 / Thariq Shihipar

让 Agent 写引擎，把玩起来的感觉留给创作者

从一个二维格斗游戏，看怎样设计人能理解、能直接改动的创作界面。

独立工程师，前 Anthropic约 19 分钟演讲中文导读与讲解 · Lila
人机交互创作控制游戏脚本
导读

先把人经常调整的决定放到看得见的地方

一句“让游戏里的角色会扔石头”，已经足以让 Agent 做出一个可运行结果。体验需要哪些决定，往往在试玩之后才明白。石头大小怎么看着舒服、墙出现时该给玩家看见什么、哪一步可以随手撤回。Thariq Shihipar 用这一段开发过程讲清楚，有些决定交给 Agent 写底层时，自己仍然想边玩边改。

他给角色可调整的行为做了一层可读脚本，着重展示从代码改一个尺寸，再回游戏查看效果。对关心使用体验的人而言，关键是运行的游戏与手里的参数用同一个定义。即便你不做游戏，也能用这套办法把频繁调整的界面行为搬到一个可以自己检查的地方。

读完可以做什么
  • 识别体验决定、稳定实现与需要新技术验证的边界。
  • 让可读脚本和运行结果引用同一处配置。
  • 用短循环记录试玩现象，把新原语交给 Agent 实现后独立核验。
上手

把一项游戏演示里的创作决定移回可读脚本

教学项目设为本地交互故事。角色在点击按钮后出现一个短暂的石块动画，墙前停住时有明显的提示。实现用任意你熟悉的工具。练习只观察画面状态，不模拟真实抛射。

第 1 步

枚举哪些决定改变体验

小功能也会带上多个默认值，先挑经常要调的两项。

展开可复制的提示词
读当前动画规格并列出可直接影响玩家理解的属性。请选择大小、停留时间、碰墙反馈中的两项，写出当前值怎么观察、谁有权改和结果如何撤回。底层绘制方式列为实现细节。

完成标志　你能解释想改的是哪一条体验，并知道怎样看出改动生效。

第 2 步

让运行时从一处可读配置取值

控件和真实表现共用一套定义，减少另存规格产生的漂移。

展开可复制的提示词
把选定属性抽到同一个配置文件。写日常中文扩展说明和字段单位。给一个正常场景和一个无效值，说明界面对无效值如何提示。为旧版保留恢复点。

完成标志　改一个字段后重新加载，实际尺寸或可见反馈与配置一致，未知字段有可理解提示。

第 3 步

一次只改一个值并试玩

一轮只有一个变化，才能知道是哪项把画面改顺了。

展开可复制的提示词
固定场景和角色，记录变更前后同样动作的截图。先只调大小并试玩，再回到基线试提示变化。展示两次的输入、结果和重新选择依据。

完成标志　对同一动作有可并排复核的前后图，并能撤回一种候选效果。

第 4 步

需要新能力时只添加必要原语

现有配置无法表达的行为，要保留边界和参考。

展开可复制的提示词
如果要支持两个可选的墙反馈，给 Agent 一份新原语规格，固定旧配置的行为。列出新增输入、可观察输出、失败时提示，并预先写两个小型回归场景。验证后让创作者在同一层调用。

完成标志　模型扩展底层组件后，旧场景行为没变，人能读懂并直接切换新反馈。

第 1 节

给工具预测留一点修正空间

能力不足时，一条能跑通的路径很有价值。等模型能走几条路以后，再从人的工作方式出发选工具和界面。

回看这一节 · 08:38:09 ↗

演讲里 Shihipar 提到自己关于 Bash、MCP 和 React 的预测后来变化。选择接口时可以先问，当前复杂任务要求什么能力，再问有几种方法都实现得了。对已经能稳定完成的工作，维护与体验常常比沿用最熟悉的模型工具更值得比较。

第 2 节

看看能力边界以内还能怎么做

最难的问题通常迫使团队先解决能否做出来。已经能做出来的事情，可以重新选择最方便人的交互方式。

回看这一节 · 08:41:12 ↗

第 3 节

做出了投石动作，却失去了调手感的机会

遇到能运行却很难调的功能，可以把隐含决定写出来。留意哪些决定影响体验，哪些纯属实现细节。

回看这一节 · 08:48:22 ↗

教学项目中，如果角色动画已经出现，每次试玩却要让 Agent 重写脚本，创作者会被迫等多个复杂改动一起返回。先把「出现的石块要不要挡住自己的动作提示」和「可见时长」写成独立决定。现场先只试动画时长，如果玩家没有看到墙反馈，再改提示。这样两次调整之间还能辨认影响。

第 4 节

用可读脚本保留创作决定

把现场常调的行为和单位留在一层可读脚本。设计者从脚本能看出结果，运行时也直接使用这些定义。

回看这一节 · 08:50:27 ↗

现场示范了怎么看见字段的单位、直接改值，以及回到游戏查看效果。实作中也可以给撤回留个入口，并写清遇到错误时停在哪里。把同样字段写进第二份说明只是补文档。如果运行时与规定行为来自两处，创作者仍得问 Agent 哪一份算数。

第 5 节

重新选一套更合适人的工作界面

给任何创作工具先挑一个人重复调整的决定，看看能否改成可见、可撤销、有即时结果的操作。

回看这一节 · 08:54:37 ↗

设计工具也可以遵循这个循环。编辑稿的动画节奏、手机端信息层级、邮件片段语气，都是反复比较才知道的决定。让使用者控制一个可以试验的参数，同时给复杂能力保留必要的实现帮助。评估时从一次真的编辑体验出发，看创作者是不是更快做出一个自己读得懂的改变。

练习

用这一讲的方法做一次小练习

为什么“角色可以扔石头”还不足以通过创作验收？

展开参考答案

功能描述漏掉了手感和规则。试玩时至少核对抛物路线、速度和蓄力、遇墙时的行为，以及玩家能否从画面读懂这些结果。

做一个机器人小程序时，可以怎样分出人编辑的层？

展开参考答案

让人在短脚本里控制速度、停留时间和动作顺序，底层驱动和状态机交给实现层。脚本与执行共用定义，先在安全的仿真里调整。

什么情况下一个“人可读层”会变成多余文档？

展开参考答案

当脚本只描述目标，实际运行仍使用另一份要手工同步的规则时，两处容易分歧。可让执行直接消费同一份定义，再把底层细节留给实现。

为一个经常被打断的创作流程做小实验。

展开参考答案

选一段常调整的动画或布局，分别试提示后等待与直接改参数后预览。记录一轮修改耗时、需切换窗口的次数，以及谁能解释最终效果。

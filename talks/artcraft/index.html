把创意桌面软件做成用户能改的工具

ArtCraft 用编程 Agent 尝试重做熟悉的创意应用。Brandon Thomas 说明为什么先做熟悉的交互，再让小工作室、非主流系统用户和社区参与维护。

开源创意软件桌面应用工程工作流
导读

想让一套创作工具能由使用者继续改

Brandon Thomas 先讲团队动手做一个类 Photoshop 应用的过程。最早的演示很快在社区传开，团队随后遇到实际用户的目标和反馈。这个故事用来理解开放工具的吸引力：能把自己的文件和组件带去另一个程序，或让团队根据一道工序改一个入口，都会具体影响最后完成工作的方式。

用户真正能替换的那部分，需要用工作成果衡量。只把画布、侧栏和按钮做得像旧应用，还不知道一张有多层内容的设计能否导入、编辑并交给另一位同事。Thomas 说，团队先规划各项操作、数据结构、导入器和可被脚本调用的功能，再逐步检查离所需的功能还有多远。

读完可以做什么
  • 把一项创作工作拆成可交接的工序
  • 用文件、用户任务和测试检查功能覆盖
  • 辨认什么时候该先让 Agent 试交互，什么时候要确认数据协议
上手

为一个小工作室替换批量出图工序

教学例：每周重复给宣传图裁切比例、压缩和导出。准备三张可公开的测试图片，保留画质参考，写明文件格式、颜色和命名约定。交付桌面交互样机、等效批处理入口和一份覆盖记录。

第 1 步

写出能复现的现有工序

顺手的旧工具包含不少没有写下来的人类决策。先还原一次提交给设计师的结果。

展开可复制的提示词
把现有三次导出的输入、选项、命名、色彩与实际尺寸整理成表。记录可能被覆盖或丢失的信息，标出哪类手工决策暂时要保留。

完成标志　得到一组最小输入和期望的完整输出，画布动作与文件验证分开记录。

第 2 步

保留原文件和交换格式

一旦修改结果无法交给另一个工具，使用者就要改变整条工序。

展开可复制的提示词
实现导出到独立路径。至少保留原文件与输出对应关系，检查方向、尺寸与 alpha。提供一条可在另一程序打开核验的办法，为不支持的图层或属性写清提示。

完成标志　测试文件能在替代程序重新打开，丢弃元数据需要显示，输出与原件可以分开追查。

第 3 步

给桌面和批处理同一个行为

让同一功能被人点或被程序调用时都能验收。

展开可复制的提示词
为同一张图提供桌面按钮与命令行入口。失败输出说明文件、参数和原因。对照两边的结果：比较尺寸、命名和图像内容，确保原件未动。

完成标志　同一协议出现在两种入口；异常导入被明确报告，完成的文件能复制到其他工具。

第 4 步

做一次能发现代价的真实试用

等待界面变得完整，往往比找出唯一不能迁移的工序更慢。

展开可复制的提示词
请一名设计同事按日常习惯完成这道工序。记录在哪一步绕行、哪类文件还缺兼容、出了错是否知道怎么恢复。用这份记录更新覆盖表并给改进排优先级。

完成标志　记录能看出三组输入用哪种路线处理。还未覆盖的任务带测试样本和可接受替代方式。

第 1 节

从能自己改工具的日子讲起

Thomas 的经历把“拥有软件”落到具体动作上。能不能在自己的机器上跑，是否可以取回文件，有没有接口改掉一段重复工作。

回看这一节 · 01:20:53 ↗

Thomas 不同作品里遇到的问题来自具体依赖。聊天服务器、第三方客户端、站点定制最有启发的是自己仍能组合东西。创意工作里的对应场景可能是接收他人的源文件、离线打开，或者将某道工序塞进批处理。是否开源回答能否阅读和修改代码，格式是否可迁移还要用实物测试。

第 2 节

专业用户可能只需要一道工序

一个小团队的特定岗位未必需要打开几百个功能。Thomas 看见用户开始围绕一道工序组合自己的工具，这是 ArtCraft 继续做开放应用的理由。

回看这一节 · 01:27:32 ↗

专业工作室只需要某道工序时，先找出工作人员反复伸手改参数的部分，再观察哪些参数总是从同一份模板来。职业岗位仍然知道什么构图、尺寸和命名符合交付要求，工具可以表现规则、提醒检查和保存选择。把这一次岗位习惯写进独立的小工具，还能缩小学习成本。

第 3 节

先达到能用，再衡量功能差距

图像编辑器的演示让人很快认出它的工作方式。验收还得用真实文件和典型编辑任务，把哪些功能已经好用写清楚。

回看这一节 · 01:30:05 ↗

对照 Photoshop 的常见习惯，应该同时保存两类信息。一类是用户会到哪找功能、一次要点几下。另一类是导入之后数据意味什么、哪些选项会影响后面修改。分类后可以先以熟悉的界面帮助试用，用规格检查现在做到哪步，再决定哪里适合设计新的交互。

第 4 节

通用组件怎样支持更多桌面应用

应用名单变长以后，维护成本会落到文件兼容、跨系统部署和人给建议的入口。共享实现和运行记录能帮后来的贡献者接上。

回看这一节 · 01:32:51 ↗

Thomas 将原生性能、可移植性和桌面应用的响应速度列入 Rust 路线的考虑。工程判断需要带实际用例与预算。例如为了做一个更快看见效果的工具，先看冷启动、打开代表文件和只能在低配机器触发的卡顿。对颜色配置、存储和 API 等长久约定，要把重写带来的兼容风险说清。编译或 CI 尚未承受住更多改动时，先把它当成要解决的工程关，而不是发布之后再补。

练习

用这一讲的方法做一次小练习

实作。为创作工具里的一道重复工序写一个只包含必要功能的规格。

展开参考答案

选一个岗位，如把若干分镜统一裁切并导出。写样本输入、输出尺寸和命名、两项手工操作、一个 CLI 参数，以及用几份真实文件验证的流程。

实作。设计三条验收用例来检验熟悉的界面是否真的兼容。

展开参考答案

从打开工程、修改图层后再保存、导出到另一工具三类动作选样本，比较效果、元数据和往返结果。把外观一致与文件行为分别记录。

理解检查。为什么在图像编辑器保留熟悉操作，同时做 CLI 和 MCP？

展开参考答案

桌面界面照顾已有工作习惯，CLI 和 MCP 让同一能力可以被脚本或 Agent 组合使用。

理解检查。改动生成加快后，团队还得承担哪些工作？

展开参考答案

编译、CI、打包、文件兼容、用户支持与反馈分流都需要资源。人还要判断风险较高的数据迁移和接口变动。

多 Agent 交接时，编排器凭什么判断任务已经完成？

用分布式系统的故障模型审视多 Agent 协作，显式交接证据、写入状态和并发限制。

Microsoft · Principal Software Engineer（个人分享）约 23 分钟演讲中文导读与讲解 · Lila
多 Agent 协作结果验证幂等与限流
导入

从一次超时看清交接的问题

编排器请子 Agent 为同一个告警建立工单。请求发出去以后迟迟没有回复。子 Agent 可能还在运行，也可能已经崩溃，或工单已经建成、回复却丢了。编排器只知道这次没有收到结果，下一步取决于能否从工单系统读回实际状态。

并行调查也会遇到证据问题。一个子 Agent 在共享上下文里写下「错误率下降了 80%」，另外两个把这句话写进审查记录和运行手册。汇总时看起来三份结果一致，实际都引用了同一个未经验证的判断。讲者把这些问题对应到分布式系统中的部分失败、共享状态读写、重复副作用和无界扇出。

上手

模拟一次写入成功但回复丢失

用本地表格模拟一个工单系统。准备一份巡检报告，任务是核对错误率并在确有异常时建立工单。安排两个子 Agent 提交调查，一个负责整理指标，一个负责核对时间范围。编排器负责读回结果和处理写入。

  1. 为指标保留分母和来源。给出两个观察窗口，分别为 1,000 次请求中 10 次报错、600 次请求中 6 次报错。让编排器重算错误率，记录查询范围、来源版本、数据截至时间和修订号。
  2. 给写入绑定唯一标识。用另一条经核实的模拟告警练习建单。先记录同一个动作的标识和批准，再让模拟工具把工单写入表格，但不返回成功回执。
  3. 记录未知并读回。将这次结果记为「未知」，按原动作标识查询表格。查到目标工单后改为「已确认」，并保留原超时记录。
  4. 检查并发和拒绝。假设同一目的地只允许两个并发请求，同时提交三项。前两项占用配额，第三项进入有界队列或得到明确拒绝。提交方能够看见哪项仍在等待。

练习通过的条件是两组错误率均算出 1%，重复提醒只关联一张模拟工单，超时原因和读回依据都能复查，超出配额的任务有明确状态。

证据

带着来源和时效交接事实

SAFE 由四条交接规则组成。S 要求事实附来源和时效。A 约束外部写入的重复副作用。F 给各个下游设并发预算。E 用明确状态交接结果。数据来源和判断过程也需要分开记录。例如可把「09:05 窗口内记录到 10 次错误」写成观测，把「某次部署引发这次波动」记为待验证的推断。

讲者用一个五分钟有效期说明何时复查。数据截至 09:05，09:06 被读到，09:07 决策时还可使用。09:15 来了新决策，这项记录留在档案里，但使用前需要重新读取来源。多个 Agent 引用同一份来源时，保留同一个引用标识，审阅时能顺着引用找到证据。

写入

用动作标识读回写入结果

一次批准绑定到一项具体动作。SAFE 无法保证恰好一次投递或提供自动回滚。写入超时后，结果在读回之前仍未知。编排器在调用前登记标识，调用后按这个标识查询实际结果。「已提交」记录发出了请求，「已确认」需要可查到对应效果。子 Agent 恢复时沿用工作进度，并先检查审批是否仍有效。

讲者提到租约到期后，旧执行者仍可能继续写入。类似场景可由写入端校验递增的令牌并拒绝过期请求。对于回复丢失的工具调用，交接记录应保留「可能已经执行」，再根据底层系统支持的查询和幂等机制处理。

编排

把准入和结果检查放进编排器

给每个下游单独设配额和等待时限。在启动执行前预留容量。遇到限流、排队超时或容量拒绝，显式记录原因，让上游可以做出等待、转人工或终止决定。

编排器按字段检查子 Agent 的交接结果。至少要能区分完成、部分完成、过期、未知和拒绝，保留做过什么、证据在哪里、哪些步骤未执行和已经发生的副作用。错误率等能机械复算的结论在编排器中复算，用计算结果决定是否接收。

边界

按动作风险选择交接约束

这套方案假设有一个固定编排器，规则和记录由它负责。若各 Agent 都是对等的，需要另外设计协调机制。只生成草稿、每次都有人工复核的流程，可以从明确状态和证据来源开始。涉及共享数据写入时，还需要核对批准、动作标识以及读回方式。

每次检查时效都多读一次来源，每次拒绝也要有后续负责人。任务做了一半需要撤销时，团队还得为已经发生的动作单独设计补偿步骤。

练习

核对三个交接结果

两个调查 Agent 都说错误率降了，可以发出结论吗？

展开参考答案

先追到各自引用的指标，再从原始分子和分母复算。10 ÷ 1,000 与 6 ÷ 600 均为 1%。若两份报告同源，也只是一份证据被引用两次。

工单创建请求超时，怎么交给下一班？

展开参考答案

记录「未知」和原动作标识，注明请求可能已经执行。下一班按标识读回工单，确认为已建后写回证据。查询依然无定论时，继续保留未知并按既定流程升级。

两个子 Agent 正在访问同一工具，第三个请求到了该怎么办？

展开参考答案

按这个工具的配额检查容量。已满就将第三个请求放入有界队列，或返回拒绝及原因。记录状态的责任在编排器，等待中的任务也能被查询。

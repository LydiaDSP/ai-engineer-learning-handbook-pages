Agent 越来越快，团队的交付流程卡在哪里

跟踪 Kiro Crew 从人盯一个会话到多层调度的变化，了解吞吐增长之后，测试、评审和发布怎样跟上。

AWS Kiro 产品经理约 18 分钟演讲中文导读与讲解 · Lila
Agent 编排交付吞吐质量门禁
导读

五个 Agent 同时给 PR 留意见，谁决定这一轮该停了？

Kiro 团队原来会让 Agent 处理所有评审意见。一次改完，再跑评审，下一轮仍可能提出新的命名和排版建议。这个流程自己的待办没有出口。Doug Clauson 讲到，后来团队把会阻止出货的检查和可另排期的改进分开，让每一类评审说明根据、范围和结果。

从一个人带一个会话到远程调度，解决的是人不在屏幕前时任务怎样继续。让更多会话完成以后还有新的问题。检查能不能反复执行，异常交给谁，合并后的发布能不能复现。演讲里的一连串变化可以看成同一个问题在不同工序出现，代码越快，到后半程越要说得清楚。

读完可以做什么
  • 从一条改动记录量出主要等待时间。
  • 给自动评审写出真正的阻断条件和结束规则。
  • 从已准备的发布物重做最小验证，使“已合并”和“用户可用”都有证据。
上手

用一条低风险改动练出能收尾的流程

用一个本地分支修说明、错误提示或小功能。用现有 CI 和可重复的小冒烟测试练习，先保持团队目前的发布权限。目的是看一次交付在哪里等待，够不够证据继续。

第 1 步

记录同一条变更经过了谁

会话开始与功能可用相隔的时间通常比写代码久。

展开可复制的提示词
把这项工作拆成提出改动、运行检查、评审批复、合并与发布核对。用真实记录填每段开始、结束、等待方和证据。没有记录的时间保留为未知。

完成标志　能指出一个最值得缩短的等待段，别用提交次数替代交付时间。

第 2 步

写一份评审出口

反复修订非阻断意见耗尽人和 Agent 的时间。

展开可复制的提示词
从现有工程要求列一份可检查的阻断清单，以及三类仅作建议的改进。每条意见都要带触发依据、影响和负责处理的人。给出结束条件。

完成标志　构建错误或关键回归会阻止推进；无证据的偏好不会自动重开一轮。

第 3 步

把固定检查和主观判断分开

新增专人或评审角色要能发现上一层漏掉的事。

展开可复制的提示词
为 PR 跑现有检查，然后按可读性、交互和真实验收分配检查。保留命令、实际输出、评审依据和冲突。需要产品决定的意见直接交给负责人。

完成标志　有人能从记录复现结果；两个角色对同一项给出相反结论时不会复写证据。

第 4 步

用干净环境试发布物

合并通过只能回答改动是否达到合并条件。

展开可复制的提示词
用一个干净测试环境安装同一版本的产物，运行核心的上手路径。记录安装来源、版本、执行步骤和观察到的结果，失败时交给发布负责人。

完成标志　保存一条版本可回查的冒烟记录，并知道失败该停在哪。

第 1 节

代码写快之后，先找整段流程最慢的地方

从收到一项工作到用户用上改动，按真实任务计算每段等待。只量写代码的时间，很容易漏掉排队与验收。

回看这一节 · 03:23:48 ↗

Clauson 报告，Amazon 早期在既有流程中采用 AI，观测到的改善约为 1.1 到 1.2 倍，主要缩短的是代码生成阶段。改变工作方式的 Amazon Stores 样本中位数约为 4.5 倍，按各团队历史开发速度归一化。真正能带回自己团队做的是固定一种交付口径。比如从一条修改进入工作直到目标用户能使用，再量生成、排队、修订、发布和回查各用多久。

第 2 节

会话数也要连着人能否接住来看

要比较两段时间的产量，先拆开工作类型。新功能、修复和补测试各自给用户带来的变化不同。

回看这一节 · 03:27:07 ↗

第 3 节

把等待从人工反馈移到可持续运行的流程

跟着一个会话看它在哪一步需要人回来。先区分系统缺信息、没触发，还是已经遇到需要判断的例外。

回看这一节 · 03:30:11 ↗

一件按规则补测试的任务适合装配式交接，因为输入和验收大致可预期。一个定位不清的缺陷常常在开始后才知道需要改范围，自动流程遇到复杂判断就应该交还给能调整目标的人。讲者说预览中的 Ultra Mode 把调度放到任务 Agent 上面，可以处理一些常见阻塞，无法由会话数量直接推导实际产出。

第 4 节

让评审能结束，也能说明为什么

把必须挡住合并的问题写清楚，给建议和阻断两种不同的出口。下一轮改动可以回头验证同一个问题是否真的解决。

回看这一节 · 03:34:31 ↗

教学例。错误提示修改完成后，命名评审要求换变量名，行为检查发现用户看不到下一步操作。只改变量名不解决任务。把第一条留成建议，把第二条连到错误状态的用户路径和要求，输出“阻断，缺少恢复提示”。先补行为、复跑测试并留下结果，原来两条意见现在各自有清楚的去向。

第 5 节

给产品减负，合并后继续核对

把候选功能放回产品主流程看一次。实现成本下降之后，使用者要学习、维护者要承担的成本依旧存在。

回看这一节 · 03:38:17 ↗

每周报告加入处理失败和新增功能的口径。演讲中较高的 PR 量包含测试、缺陷修复和外部贡献，讲者把新功能估为约十分之一。把新功能、维护、复验分开，团队才知道生成速度改善以后落到了哪类工作。干净环境装一次产物，可以接受为对一条用户主路径的证明，并应明确其覆盖范围。

练习

用这一讲的方法做一次小练习

十个会话都能写代码，但每个都等人说继续。这个系统下一轮该改什么？

展开参考答案

取三类常见暂停，记录停在哪步。可自动判定的情况补验证和默认下一步，真的需要业务判断的情况保留人工请求并给足上下文。

为自动评审制定两个阻断条件和两个非阻断建议。

展开参考答案

可以阻断构建失败和既有公开接口行为被破坏。可另记变量命名偏好和不影响结果的文档措辞。每种情况附证据或例子，避免同一问题被反复改。

两个模型给出了相反评审意见，谁负责决定？

展开参考答案

先确认它们评的是同一风险和版本，用测试、重现或设计约束解决分歧。没有足够证据时交给负责的工程师，保存决定供评审规则改进。

补一份能在 PR 合并后运行的最小发布检查。

展开参考答案

从干净环境安装当前合并版本，跑用户最依赖的三个流程，留下版本、输入、结果、耗时和异常处理人。安全与权限要求按产品所在环境另设对应检查。

从一个你可能遇到过的问题开始

已经提醒三次了，
为什么它还会犯同样的错？

你让 Agent 改一个界面。它做出了看起来能用的结果，却又把代码放错了地方。你解释原因，在 AGENTS.md 里加了一条规则。下一次，它换了一个写法，还是绕回同一个坑。

再写一段更严厉的提示，当然可以试。但 Lauren 在这场演讲里提出了另一条路线：能不能改变代码库本身，让这个错误被自动发现，或者让它根本没有那么容易发生？

她以团队开发桌面客户端的经历为例，讨论如何在大量 Agent 持续提交代码时保持质量。演讲中的限制措施、交付数字和效果均来自讲者的经验陈述。本章关注的是背后的工程方法，而不是把某个团队的规则直接照搬到所有项目。

读完这一章，你应该能回答
  • 哪些纠正适合变成代码检查，哪些仍然需要文字和人的判断？
  • Agent 说“已经修好了”和提供验证证据，有什么区别？
  • 为什么“更多自动化”之前，应该先改善每一轮写代码的过程？

下面先顺着这三个问题理解演讲。需要确认讲者究竟怎么说时，点击各节的“查看对应原文”。

快速上手 / 从一次小改动开始

先做一轮，
让 Agent 证明它改对了。

你不需要先掌握所有工程术语。这份指南把本章的方法转成一次小练习：挑一个反复出现的问题，让 Agent 找到原因、做最小修改，并提供你能检查的结果。以下步骤和提示词是编辑设计的练习，不是 Lauren 的原话或官方操作流程。

第一次读这本手册

想先实践：按下面四步试一次，遇到不理解的概念再看讲解。想先弄懂原理：从“信任从环境里长出来”继续阅读。想核对演讲：到全文区选择中文、英文或中英对照；PPT 可切换语言、点击放大。

准备：一个项目，一个可重复的问题

打开一个你正在用编程 Agent 修改的项目，选一件范围小、结果看得见的事。例如“点一次保存，偶尔生成两条相同记录”。先在本地或测试环境操作，并保存当前版本。没有现成项目，也可以先用这个案例练习写清验收条件。

第 1 步 · 说清楚什么才算做对

把抱怨换成可以观察的行为。

写下操作步骤、现在发生的事、你期待的结果。以保存按钮为例：连续点击两次，只新增一条记录；保存失败时保留输入，并允许重试。这里的条件是教学示例，你需要按自己的产品确认。

可直接复制：先调查，先别改代码
我想处理这个重复问题：〔填写具体问题〕。
复现步骤：〔填写点击或输入过程〕。
当前结果：〔实际发生什么〕。
预期结果：〔希望发生什么〕。

先阅读相关代码，不要修改。请告诉我：
1. 你找到了哪些相关文件和已有约定？
2. 可能的原因是什么？哪些还需要验证？
3. 怎样复现，并用明确条件判断修复成功？
请用我能理解的语言解释，必要术语附一句说明。

这一步完成的标志：你能说清“怎么让问题出现”和“修好后应该看到什么”。如果 Agent 找不到复现方式，先把现象或不确定性补清楚。

第 2 步 · 选最小的解决办法

判断是补检查，还是改接口。

让 Agent 比较：这是漏了一项检查，还是现有接口本身容易被误用？规则明确时可以增加自动检查；接口有缺陷时，单纯加禁令可能只会让它换一种方式绕过去。无需为了练习搭建一整套工具。

可直接复制：比较方案并说明取舍
基于刚才的调查，请给出解决这个问题的最小方案。
说明适合增加测试或静态检查，还是需要调整现有接口，以及理由。
列出必要的修改范围、正常行为和可能的例外。
优先使用项目已有工具，不要扩大到无关重构。
哪些判断需要我决定，请明确指出。

这一步完成的标志：你知道要改哪里、为什么这样改，以及这个方案不能解决什么。看三个工程案例 →

第 3 步 · 修改，同时提供前后证据

让检查能发现旧错误，也能验证新结果。

确认方案后再让 Agent 实施。检查的价值不只是显示“通过”：它应该确实能识别原来的问题。能复现时，先记录失败，再验证修改后的行为；无法安全复现时，应明确说明限制。

可直接复制：实施与验证
按我们刚才确认的方案做最小修改。
请先记录原问题的复现结果，再验证修改后的同一操作。
如果适合自动检查，使用项目已有工具，并确认检查能发现原来的错误。
同时检查相关的正常操作和失败情况。
给我具体的执行结果；界面问题请附截图或操作视频。
区分“实际运行验证了什么”和“只是推测可能正确”。
如果无法运行，请说明原因，不要把未验证写成已通过。
本次先保留在本地，不发布或自动合并。

这一步完成的标志：你拿到了与验收条件对应的证据，而不只有“已修复”的总结。看怎样审查验证证据 →

第 4 步 · 自己复查，并留下下一次能用的约束

走一次关键流程，确认规则会继续执行。

亲自按第一步操作一遍，检查结果是否符合预期。再让 Agent 说明新增检查什么时候运行、发现问题时会怎样提示。只有放进实际开发流程的检查，才有机会阻止下一次重犯。

可直接复制：检查这次改动留下了什么
请总结这次改动：
- 哪条验收条件由什么证据支持？
- 新增检查或接口约束是什么，什么时候执行？
- 下次出现同类错误，它会怎样暴露问题？
- 还有哪些未覆盖的情况或需要人工判断的部分？
请给我一份简短的人工复查步骤，不要只重复“测试通过”。

这一步完成的标志：你能解释这次为什么可信，也知道仍有哪些边界。如果同一问题再次出现，回到原因和检查覆盖范围，不急着再加一条提示词。

第一次实践，做到“一个明确问题 + 一个最小改动 + 一份可检查证据”就够了。更复杂的形式化验证，可以在理解本章之后按需要学习。

01 / 核心思路

信任来自环境，
不是一句“相信你”。

Lauren 把工程师的新任务描述为：在大幅提高产量的同时，维持甚至改善质量。她并不是把“信任 Agent”理解成少检查一点，而是先投入时间，改造 Agent 工作的环境。

这个环境首先是代码库。Agent 会从已有代码中推断“这里通常怎么做”。如果某种临时补丁到处都是，它就可能把补丁当作惯例继续复制。反过来，清晰的接口、稳定的结构和好的范例，也会持续影响它的输出。

代码库既是 Agent 的工作对象，也是它不断阅读的范本。

编辑概括 · 对应 01:04:28—01:06:20

她用“园艺”打比方：新增代码像不断生长的植物，代码库里的架构和约束像它们绕着生长的基础。于是，工程师的工作不只是在终点挑出坏代码，也是在起点修整环境。

补一点基础：代码库、API、PR 分别是什么？

代码库是项目代码、配置、测试等材料的集合。API可以理解为不同部分之间约定好的调用入口。PR（Pull Request）是一份等待审查和合并的代码变更提案；合并不一定等于发布上线。

这里的“环境”也不只是电脑配置，还包括哪些接口可用、哪些规则会执行、如何运行应用，以及什么证据能支持完成判断。

02 / 三个具体案例

把一次纠正，
变成下一次会执行的检查。

Lauren 给出一个可以立刻拿来思考的原则：每次纠正 Agent 时，先想想是否能形成确定性检查，或者通过接口与架构消除这一类问题。它的价值在于：检查不依赖 Agent 每次都想起那段提示。

A

把复杂 API 收进受控边界

她说，React 的 useEffect 有适用场景，但很容易被误用。团队的做法是限制产品代码直接使用它，只在框架 Dune 的部分 API 内允许使用。复杂性仍然存在，却被集中到了更容易控制的位置。

怎样理解：要学的是“把容易误用的能力收进清晰接口”，不是“所有项目都禁用 useEffect”。React 官方把它用于与外部系统同步；具体是否限制，要看你的框架和需求。官方说明 ↗

B

让目录表达职责，让工具执行边界

在 Electron 桌面应用中，她用 electron-renderer 和 electron-main 两个目录区分职责，并用依赖图分析器和 lint 规则禁止不合规的相互导入。目录名帮助理解；真正执行边界的是检查工具。

一个关键细节：只把目录重命名，并不能自动阻止错误。还要有工具发现越界，并在开发流程中真正执行。

C

不要让“解释得通”代替“修到根因”

Lauren 讲到，Agent 曾经用大量定时器绕过架构冲突，并写下注释解释这些临时办法为什么合理。补丁被复制，性能问题也随之扩散。团队后来限制大量注释，并让 lint 错误提示引导 Agent 修复根因。

这个故事提醒我们：一段解释不能强制后续代码遵守它，也不能替代运行验证。但“注释无法强制执行”和“注释没有价值”是两回事。必要的设计理由、约束背景和例外说明，仍需要由人判断如何保存。

进一步理解：lint 与测试有什么不同？

lint通常在不运行整个应用的情况下，检查代码是否违反约定或存在特定模式。测试则在选定条件下执行代码，观察结果是否符合预期。两者解决的问题有交集，但无法相互完全替代。

例如，“这个目录不允许导入那个模块”适合静态检查；“快速切换对话时是否显示了错误消息”通常还需要运行层面的验证。

03 / 验收方式

“我改好了”，
还不是验证证据。

当一部分常见错误被环境和检查接管，Lauren 说团队的审查重心开始转向验证产物：视频、截图、图表和形式化验证结果。这个变化值得细看：人仍然要判断，只是判断对象发生了变化。

运行时验证最直观：让 Agent 能启动应用、操作功能、使用调试工具，而不是只检查自己刚写的文字。她还介绍了“功能地图”，从用户视角描述应用中的功能，让“左边栏里那个东西”变成双方可以准确引用的名称。

教学示例 · 不是演讲中的原案例

让 Agent 修复“切换会话时显示错内容”

只有完成报告

“已修复切换问题，测试通过。”

不知道它操作了什么，也不知道验证覆盖哪些场景。
可检查的验证记录

打开会话 A → 切到 B → 快速返回 A；记录画面、预期内容与实际内容，并附相关测试结果。

可以追问操作条件、失败场景和结果是否一致。

她使用自定义 CLI，让 Agent 复用命令行工具和驱动，避免每次临时拼一套操作。这里有两层价值：操作方法更一致，工具本身也更容易测试。工具复用并不意味着每次验证都可以省略。

补一点基础：CLI、功能地图、验证产物

CLI是命令行接口；你可以把它理解为“用一条明确命令启动一组约定好的操作”。功能地图是人和 Agent 对应用功能的共同索引。验证产物是可审查的结果记录，如截图、视频、测试报告。

截图只能说明某个时刻的画面，视频可以展示一段交互，测试报告说明特定检查的结果。单一产物通常不能证明所有需求都被满足。

04 / 深入一层

不同验证方法，
回答不同的问题。

Lauren 提到运行时验证、TLA+ 模型检验、Lean 以及 UI 属性测试。它们不是从低级到高级、最后互相取代的一条阶梯。更好的理解方式是：你担心什么错误，就需要能发现那类错误的方法。

她举到跨设备通知、虚拟化库和 UI 缺陷等例子，但没有在这段演讲中展示足够细节，让我们复现全部模型与证明。因此，本章不把它改写成“用 Lean 就能保证界面永远不闪烁”的教程。

进一步理解：为什么“证明正确”仍然有边界？

你首先需要写清楚要证明什么，以及允许哪些前提。一个数学命题被证明，并不自动意味着部署环境、数据输入、需求定义和整套应用都已验证。

TLA+ 侧重精确描述系统的状态与行为；Lean 是编程语言和证明助手。二者都要求你认真对待规格本身。演讲中“帮忙理解产品应该怎样工作”这一点，与最终检查结果同样值得重视。

05 / 读懂结果，而不只记住数字

产量、回退率、性能，
要放在一起看。

Lauren 用团队的结果说明这套投入的回报：上个月约 11,000 个 PR、约每日一个稳定版、十月约 227 位贡献者、口述的 PR 回退比例约 0.5%（原图按提交统计），以及多项客户端性能改善。这些是演讲中的团队自述，没有在本章中独立审计。

11,000讲者所述上月团队 PR 数
≈ 0.5%原图的提交回退率水平
≈ 每日讲者所述稳定版发布节奏

原图补充：口头转写将约 0.5% 说成 PR 回退比例，但幻灯片明确标注为“被回退的提交（commits）占比”。提交与 PR 不是同一单位，本章保留两种来源表述，不把它们强行统一。

数量回答“做了多少”；回退率提供一部分质量信息；性能反映某些用户体验结果。它们相互补充，但仍无法单独说明每个变更的价值、全部线上缺陷或总维护成本。没有回退的 PR，也不一定没有问题。

同样要区分个人与团队数据。开场英文转写把个人的约 3,000 次写成“deploy requests”，但实际 PPT 写的是“3,000 PRs”。这处识别疑点已随原文标注；它与后面的团队 11,000 个 PR 也不能混为同一个统计对象。

性能页同时展示了改善和退步：例如冷启动从 2,304 ms 降至 1,395 ms，但空闲内存从 488 MiB 增至 545 MiB，空闲 CPU 从 0.40% 增至 0.80%，调整窗口大小也变慢了。讲者的“多项改善”并不意味着每一项都改善。

如果内层写代码的循环不断产生问题，外层自动化只会更快地复制它们。

06 / 用一次，才知道自己是否理解

下一次纠正 Agent，
试着多问一步。

不需要先学会 TLA+。从一个你已经遇到过的重复错误开始，判断它究竟是规则不清、接口容易误用，还是缺少验证。

练习 01

数据请求总被放错位置，怎么办？

你要求 Agent 统一通过项目的数据接口访问服务，它却经常在页面里直接发请求。你会加一句提示、加检查，还是调整接口？

展开参考分析

先确认约定是否明确，统一接口是否真的覆盖需求。若接口不好用或缺少能力，单加禁令可能促使 Agent 绕路。若边界明确且接口足够，可以增加检查，并提供正确使用范例和有帮助的错误信息。必要例外要显式处理。提示、接口和检查可以配合，不是只能选一个。

练习 02

一段成功视频，足以自动合并吗？

Agent 提供视频证明按钮能正常保存，但你没有看到网络失败或重复点击的情况。

展开参考分析

视频支持“这次成功路径能运行”，并没有覆盖失败路径。先确定需求和风险，再补充网络失败、重复提交等相关检查。证据足不足，取决于变更影响；不能因为“有视频”就自动认为完成了验收。

练习 03

团队回退率很低，说明什么？

一个团队报告 0.5% 的 PR 回退率，你能据此认定它比另一个团队的软件质量更好吗？

展开参考分析
